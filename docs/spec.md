## 1. Общее описание и технологии

### Описание

«Голодные змейки 🐍» — браузерная 2D-игра на HTML5 Canvas. Игрок управляет змейкой, которая перемещается по клеточному полю, поедает еду (базово — яблоки), избегает стен и других змеек. Игра поддерживает от 0 до 2 игроков-людей и от 0 до 4 ботов одновременно. Игра разделена на уровни с нарастающей сложностью.

### Технологии

| Параметр | Значение |
|---|---|
| Язык | TypeScript (strict mode) |
| Сборка | webpack (dev server + production build) |
| Рендер | HTML5 Canvas 2D API |
| Тесты | Jest + ts-jest (среда jsdom) |
| Вёрстка | Адаптивная, игровое поле по центру экрана |
| Стили | Только CSS-классы и CSS custom properties (переменные). **Inline-стили запрещены** |
| Интерфейс | Полностью на **русском** языке |
| Хранение данных | `localStorage` (рекорды, имена игроков, настройки dev-режима) |
| Округление | `Math.floor()` для всех вычислений, дающих дробное число |

### Принцип модульности

Проект разделён на два независимых слоя:

- **Engine** — чистая логика: состояние игры, движение, коллизии, спавн, формулы. Не зависит от DOM и Canvas. Покрывается unit-тестами.
- **Renderer** — отрисовка текущего состояния на Canvas. Не содержит игровой логики.

Все сущности (змейки, еда, стены) хранятся в отдельных массивах внутри `GameState`. Двумерный массив `board[][]` пересобирается из сущностей каждый тик для отладки и AI.

## 2. Режимы игры

### Комбинации участников

Поддерживаются любые комбинации, удовлетворяющие ограничениям:

| Параметр | Допустимые значения |
|---|---|
| Игроки-люди | **0, 1 или 2** (не более 2) |
| Боты (AI) | **0, 1, 2, 3 или 4** |
| Суммарно змеек | От 1 до 6 |

#### Режим наблюдателя (0 игроков)

Если игроков-людей **0**, боты играют между собой. Пользователь только наблюдает. Управление клавиатурой не привязывается ни к одной змейке. Пауза по пробелу всё равно доступна.

#### Одиночный режим

Одиночный режим имеет 2 подрежима:

1. **Классика (1 игрок, 0 ботов)**:
   - цель — пройти уровни, набирая кумулятивный порог очков;
   - общее количество уровней: **10**;
   - после завершения 10-го уровня игра заканчивается.
2. **Выживание (1 игрок, 0 ботов)**:
   - общее количество уровней: **100**;
   - переход на следующий уровень происходит при достижении целевого счёта текущего уровня;
   - переход выполняется автоматически, **без паузы и без модалки конца уровня**;
   - после успешного завершения уровня 100 игра заканчивается победой.

#### Многопользовательский / смешанный режим

Любая комбинация с ≥2 змейками. Уровень заканчивается по выживаемости или таймеру. После уровня 10 игра завершается и определяется итоговый победитель по победам и очкам.

### Сложность

| Параметр | Значение |
|---|---|
| Диапазон | **1–10** (целое число) |
| По умолчанию | **1** |
| Выбирается | В меню перед началом игры |

Сложность влияет на:
- Длину генерируемых стен (больше → длиннее)
- Количество начальной еды (больше → меньше еды)

## 3. Управление

### Управление змейками

Игра поддерживает одновременное управление двумя игроками на одной клавиатуре:

| Игрок | Вверх | Влево | Вниз | Вправо |
|-------|-------|-------|------|--------|
| Игрок 1 | `W` | `A` | `S` | `D` |
| Игрок 2 | `↑` (ArrowUp) | `←` (ArrowLeft) | `↓` (ArrowDown) | `→` (ArrowRight) |

Каждый набор клавиш привязывается к соответствующей змейке по порядку: первый человек в списке — WASD, второй — стрелки.

Дополнительное правило:
- В режиме **1 игрок** управление первой змейкой принимается **одновременно** и от WASD, и от стрелок.
- В режиме **2 игрока** схема остаётся классической: игрок 1 — WASD, игрок 2 — стрелки.

#### Правила обработки ввода

1. **Запрет разворота на 180°**: если змейка движется вправо, нажатие «влево» игнорируется. Аналогично для всех направлений. Змейка сохраняет прежнее направление.
2. **Одно направление за тик**: если игрок нажал несколько клавиш между тиками, применяется **последнее** нажатие (которое не является разворотом на 180°).
3. **Направление применяется в начале тика**, до расчёта движения.

### Touch-управление

При обнаружении touch-устройства показываются onscreen-кнопки управления.

#### Режим 1 игрок

- В левом нижнем углу игрового блока: кнопки `←` и `→`.
- В правом нижнем углу игрового блока: кнопки `↑` и `↓`.
- Кнопки работают как дополнительный источник направления для игрока 1 и подчиняются тем же правилам буфера ввода (последнее валидное направление за тик).

#### Режим 2 игрока

Touch-раскладка для двух игроков (кнопки для обеих сторон экрана без поворота HUD) реализуется отдельным этапом и уточняется в разделе 18.

### Пауза

| Клавиша | Действие |
|---------|----------|
| **Space** (Пробел) | Контекстное действие — зависит от текущего состояния |
| **Escape** | Контекстное действие выхода/отмены (см. ниже) |
| **Enter** | Подтверждение в модалках выбора `Да / Нет` |

Поведение клавиши «Пробел»:

| Текущее состояние | Что происходит при нажатии Space |
|-------------------|----------------------------------|
| Игра идёт (нет модалки) | Ставит игру на **паузу**: game loop останавливается, появляется модальное окно «ПАУЗА» |
| Модалка «ПАУЗА» | Снимает паузу: модалка закрывается, game loop продолжает работу |
| Модалка «Конец уровня» | Закрывает модалку и переходит к следующему уровню (аналогично кнопке «Продолжить») |
| Модалка «Игра окончена» | Закрывает модалку и переходит на экран результатов |

Примечание: в режиме выживания модалка «Конец уровня» не используется, поэтому переход по Space для этого состояния не применяется.

Поведение `Escape`:
- В состоянии **Playing**: игра ставится на паузу и открывается модалка подтверждения выхода (`Да/Нет`).
- В состоянии **Paused**: мгновенный выход в главное меню.
- На экране **Results**: возврат в главное меню.
- В модалке подтверждения: `Enter` = подтвердить выход (`Да`), `Escape` = отменить (`Нет`) и вернуться в игру.

Во время паузы:
- Game loop полностью остановлен (тики не идут)
- Таймер уровня не убывает
- Canvas замораживается на последнем кадре
- Поверх поля появляется модальное окно с затемнённым overlay

В **dev-режиме** модалка паузы покрывает **только игровую область** (canvas, HUD-панели), но **не панель настроек** справа — она остаётся кликабельной.
## 4. Игровое поле

### Размер поля

Размер поля зависит от текущего уровня:

```
ширина = baseWidth  + (level − 1) × levelSizeIncrement
высота = baseHeight + (level − 1) × levelSizeIncrement
```

Значения по умолчанию (из `gameDefaults.json`):

| Параметр | Значение |
|---|---|
| `baseWidth` | 40 |
| `baseHeight` | 40 |
| `levelSizeIncrement` | 2 |
| `survivalMaxBoardLevel` | 10 |

Примеры: уровень 1 — 40×40, уровень 2 — 42×42, уровень 3 — 44×44.

В режиме выживания рост активного поля ограничен уровнем `survivalMaxBoardLevel` (по умолчанию 10). Поэтому уровни 10–100 используют максимальное активное поле 58×58. Визуальный canvas сразу создаётся под этот максимальный размер, а поле уровня 1 располагается по центру. При повышении уровня границы активной области раскрываются симметрично наружу на одну клетку с каждой стороны; размер canvas и масштаб клеток при этом не меняются.

### Внутреннее представление (engine)

Поле представлено двумерным массивом `CellContent[][]` (строковые маркеры):

| Символ | Значение |
|--------|----------|
| `' '` (пробел) | Пустая клетка |
| `'&xN'` | Еда, где `N` — очки за поедание текущей фазы (например, `&x2` для взрослого яблока) |
| `'*'` | Стена / преграда |
| `'1'..'6'` | Сегмент тела змейки по `snake.id + 1` (`1` — первая змейка, `2` — вторая, `3..6` — боты) |

Массив `board[][]` **пересобирается из сущностей** каждый тик (не является мастер-данными). Мастер-данные — отдельные массивы `state.walls`, `state.foods`, `state.snakes`.

### Границы поля

Границы поля являются непроходимыми: выход за пределы координат `[0, width)` × `[0, height)` считается столкновением со стеной и вызывает смерть змейки. Отдельных стен по периметру нет — граница неявная.

### Координатная система

- Ось **X** — горизонтальная, растёт слева направо (0 = левый край).
- Ось **Y** — вертикальная, растёт сверху вниз (0 = верхний край).
- Клетка `(x, y)` рисуется как прямоугольник `[x × cellSize, y × cellSize, cellSize, cellSize]`.

## 5. Змейки

### Структура данных

Каждая змейка хранится как объект `Snake`:

```typescript
interface Snake {
  id: number;               // уникальный идентификатор (0, 1, 2…)
  name: string;             // имя (из меню или «Бот N»)
  segments: Position[];     // массив координат, segments[0] = голова
  direction: Direction;     // текущее направление ('up' | 'down' | 'left' | 'right')
  alive: boolean;           // жива ли
  score: number;            // очки за еду и бонусы за выживание в завершённых раундах
  levelsWon: number;        // количество выигранных уровней
  ticksWithoutFood: number; // тиков без еды (для механики голода)
  isBot: boolean;           // управляется ли AI
  movementPaused?: boolean; // техническая остановка движения при потере сетевого соединения
  deathReason?: string;     // причина смерти (если мертва)
}
```

### Начальные параметры

| Параметр | Значение по умолчанию |
|---|---|
| Начальная длина | **5** сегментов (`initialSnakeLength`) |
| Начальное направление | Зависит от стартовой позиции |
| `ticksWithoutFood` | 0 |
| `score` | 0 |
| `levelsWon` | Переносится между уровнями |

### Стартовые позиции

Змейки размещаются на заранее рассчитанных позициях, распределённых по полю. Стартовые позиции зависят от размера поля и количества змеек. Между стартовой позицией и краем поля оставляется отступ не менее `initialSnakeLength + 2` клеток.

Тело змейки при старте вытянуто в направлении, **противоположном** начальному направлению движения. Пример: если змейка стартует в позиции `(7, 20)` с направлением `right`, её голова в `(7, 20)`, следующий сегмент в `(6, 20)`, потом `(5, 20)` и т.д.

### Движение

1. Каждый тик змейка перемещается ровно на **1 клетку** в текущем направлении.
2. Перемещение реализовано как:
   - Вычисление координаты новой головы (`getNextHeadPosition`).
   - Добавление новой головы в начало массива `segments`.
   - Удаление последнего сегмента (хвоста) — если змейка НЕ ест еду.
   - Если змейка ест еду — хвост НЕ удаляется, змейка растёт на `food.growthValue`.
3. При технической потере сетевого соединения змейка получает `movementPaused = true`: она не перемещается до переподключения или передачи управления боту, но остаётся живой и видимой, участвует в коллизиях, а её голод продолжает увеличиваться.

### Смерть змейки

Змейка погибает (поле `alive = false`) в следующих случаях:

| Причина | Когда проверяется | `deathReason` |
|---------|-------------------|---------------|
| **Столкновение со стеной** | Новая голова попала на стену или за границу поля | `'Врезалась в стену'` |
| **Столкновение с другой змейкой** | Новая голова попала на сегмент другой живой змейки | `'Столкнулась с другой змейкой'` |
| **Самоукус** | После перемещения голова совпадает с любым другим сегментом той же змейки | `'Съела саму себя'` |
| **Голод** | После потери сегмента длина стала < `minSnakeLength` (по умолчанию 2) | `'Умерла с голоду'` |

#### Порядок проверок в тике:

1. Вычисляется новая позиция головы.
2. Проверяется столкновение со стеной → если да, змейка погибает, **пропуск оставшихся шагов**.
3. Проверяется столкновение с другими змейками → если да, змейка погибает.
4. Выполняется перемещение (голова добавляется, хвост удаляется или нет).
5. Проверяется самоукус → если да, змейка погибает.
6. Если новая голова совпадает с позицией еды → еда съедается.

### Поедание еды

Когда голова змейки оказывается в клетке, где находится еда:

1. Еда **удаляется** из массива `state.foods`.
2. Змейка растёт на `food.growthValue` сегментов.
3. Счёт змейки увеличивается на `food.scoreValue`.
4. Счётчик голода **сбрасывается** (`snake.ticksWithoutFood = 0`) для **любой** еды.

### Голод

Механика голода стимулирует змейку активно искать пищу:

| Параметр | Значение по умолчанию |
|---|---|
| `hungerThreshold` | **15** тиков |
| `minSnakeLength` | **2** сегмента |

**Алгоритм (каждый тик, после движения):**

1. `ticksWithoutFood++`.
2. Если `ticksWithoutFood >= hungerThreshold`:
   - Удаляется последний сегмент (хвост) — змейка укорачивается на 1.
   - `ticksWithoutFood` сбрасывается в **0**.
   - Если `segments.length < minSnakeLength` → змейка **погибает** с причиной `'Умерла с голоду'`.

Таким образом, если змейка не ест, она теряет по 1 сегменту каждые `hungerThreshold` тиков, пока не останется менее 2 сегментов и не умрёт.

### Мёртвые змейки

После смерти змейка **не исчезает** с поля:

- Её тело остаётся на месте до конца уровня.
- Визуально мёртвая змейка отображается **серым цветом** (обесцвечивание).
- Коллизии с мёртвыми змейками **не проверяются** (другие змейки могут проходить сквозь мёртвое тело).
- При смерти от любого столкновения тело однократно создаёт мясо из расчёта один кусок на три сегмента с округлением вверх; при смерти от голода мясо не создаётся. Подробный алгоритм размещения описан в разделе 6.7.

### Визуальное отображение змейки

#### Тело (живая змейка)

- Каждый сегмент занимает одну клетку (`cellSize × cellSize`).
- Заливка: **базовый цвет** змейки (из палитры `snakeColors`).
- Обводка каждого сегмента: тонкая линия (`lineWidth: 1`), цвет на **35% темнее** базового.

#### Голова (живая змейка)

- Заливка: базовый цвет, затемнённый на **25%** (темнее тела).
- Обводка: **белый** (`colorHeadStroke`, по умолчанию `#FFFFFF`), `lineWidth: 1`.
- Два **чёрных глазка**: маленькие круги (`radius = max(1, cellSize × 0.12)`), расположенные со стороны направления движения. Отступ от края клетки: `cellSize × 0.25`.
  - Направление `up` → глаза у верхнего края (левый и правый).
  - Направление `down` → глаза у нижнего края.
  - Направление `left` → глаза у левого края (верхний и нижний).
  - Направление `right` → глаза у правого края.

#### Мёртвая змейка

- Все сегменты (включая голову) закрашиваются **серым** (обесцвеченный базовый цвет: `grey = round(r×0.3 + g×0.3 + b×0.3)`).
- Обводка каждого сегмента: цвет на **35% темнее** серого.
- Глазки **не рисуются**.

#### Палитра змеек

Цвета назначаются по порядку (по `snake.id`):

| # | Цвет по умолчанию |
|---|---|
| 0 | `#00FF00` (зелёный) |
| 1 | `#00CCFF` (голубой) |
| 2 | `#FFFF00` (жёлтый) |
| 3 | `#FF00FF` (пурпурный) |
| 4 | `#FF8800` (оранжевый) |
| 5 | `#88FF88` (светло-зелёный) |

Если змеек больше чем цветов — палитра зацикливается.
## 6. Еда (Food)

### 6.1 Доменная модель еды

Еда реализуется через базовый класс `Food` и наследников (минимум `AppleFood`, `RabbitFood`, `ChickenFood`, `MeatFood`).

```typescript
interface Food {
  id: string;
  kind: 'apple' | 'rabbit' | 'chicken' | 'meat' | string;
  pos: Position;
  age: number;               // абсолютный возраст в тиках
  clockNum: number;          // тиков с рождения/последнего размножения
  reproductionCount: number; // сколько раз размножалась сущность
  phase: 'young' | 'adult' | 'old';
  scoreValue: number;        // сколько очков даёт при поедании
  growthValue: number;       // на сколько сегментов растёт змейка
}

interface ChickenFood extends Food {
  kind: 'chicken';
  originPos: Position;       // место появления яйца для ограничения цыплёнка
  movementClock: number;     // отдельный счётчик частоты перемещения
  pendingMandatoryEgg?: boolean; // legacy-поле совместимости; Engine его игнорирует
}
```

Общие правила:
- возраст (`age`) и логика фаз — в базовом `Food`;
- размножение — общее поведение базового `Food`, с возможностью уточнения в наследниках;
- сброс голода змейки при поедании работает для **любой** еды.

Требование совместимости доменной логики:
- всё поведение, которое ранее было определено для кроликов (жизненный цикл, размножение, ограничения соседства, правила размещения и удаления по возрасту), считается **базовым поведением `Food`**;
- дочерние классы (`AppleFood`, `RabbitFood`, `ChickenFood`, `MeatFood` и другие) могут расширять или переопределять это поведение.

### 6.2 Активные типы еды по режимам и уровням

- **Классика (1P) и мультиплеер (2+ змейки)**: уровни `1..10`; на первом уровне используется только `AppleFood`, далее действует смесь яблок и куриной еды.
- **Выживание (1P Survival)**: уровни `1..100`; на первом уровне используется только `AppleFood`, далее действует смесь яблок и куриной еды.
- На уровне 1 создаются только яблоки. Начиная с уровня 2 каждое место штатного начального спавна или автодобавления с вероятностью `30%` занимает `ChickenFood`, а с вероятностью `70%` — `AppleFood`. Выбор выполняется через переданный seeded RNG.
- Независимый периодический спавн выполняется каждые 100 тиков и использует отдельную, зависящую от количества яблок вероятность типа еды, описанную в разделе 6.10.
- Потомок при обычном размножении сохраняет тип родителя; правило `30%` к размножению не применяется.
- `RabbitFood` остаётся поддерживаемым типом для расширений/экспериментов, но в базовом режиме не обязателен к включению в первые уровни.

### 6.3 Начальный спавн еды

При инициализации уровня генерируется начальное количество еды:

```
foodCount = Math.floor(foodCountPerSnakeCoeff × snakeCount + foodCountBase − difficultyLevel)
```

Значения по умолчанию: `foodCountPerSnakeCoeff = 1.5`, `foodCountBase = 5`.

Состав стартовой еды:
- сначала для каждого места выбирается тип еды по правилу уровня;
- любой штатно созданный `ChickenFood` появляется яйцом с `age = 0`;
- среди созданных яблок до `snakeCount` единиц получают фазу `adult`, остальные яблоки — `young`.

Правила размещения:
1. Не на стене.
2. Не на живой змейке.
3. Расстояние Чебышёва до любой другой еды > 1.
4. Внутри границ поля.

Если за `count × 100` попыток не удалось разместить всю еду — размещается столько, сколько получилось.

### 6.4 Жизненный цикл еды (общий)

У каждой еды есть абсолютный возраст `age`, который увеличивается на 1 каждый тик.

| Фаза | Диапазон `age` (по умолчанию) |
|------|-------------------------------|
| `young` | `0 ≤ age < 50` |
| `adult` | `50 ≤ age < 100` |
| `old` | `100 ≤ age < 150` |

На тике, когда `age >= maxAge` (по умолчанию `150`), еда удаляется с поля, если дочерний тип не задаёт преобразование или другой предел возраста. Курица вместо удаления превращается в мясо, а `MeatFood` использует собственный `maxAge = 50`.

Параметры жизненного цикла:
- `foodYoungAge = 50`
- `foodAdultAge = 100`
- `foodMaxAge = 150`

### 6.5 Значения еды по умолчанию (`AppleFood`)

Для яблок используются 3 стадии и их ценность:

| Стадия | Фаза | Цвет | Очки | Рост |
|--------|------|------|------|------|
| Маленькое | `young` | Зелёный | `+1` | `+1` |
| Взрослое | `adult` | Красный | `+2` | `+2` |
| Старое | `old` | Коричневый | `+1` | `+1` |

### 6.6 Куриная еда (`ChickenFood`)

`ChickenFood` использует общие возрастные границы, но отображает их как последовательные стадии развития:

| Стадия | Фаза | Возраст | Значок | Очки | Рост | Поведение |
|--------|------|---------|--------|-----:|-----:|-----------|
| Яйцо | `young` | `0..49` | 🥚 | `+1` | `+1` | Неподвижно |
| Цыплёнок | `adult` | `50..99` | 🐤 | `+2` | `+2` | Случайный шаг раз в 3 тика, не дальше 5 клеток от позиции яйца |
| Курица | `old` | `100..149` | 🐔 | `+3` | `+3` | Раз в 2 тика идёт к яблокам, а без яблок — туда, где меньше змеек |

При создании яйца его позиция сохраняется как `originPos`. Цыплёнок за один ход перемещается на одну из восьми соседних клеток на расстоянии 1 по Чебышёву и не может выйти за радиус 5 по Чебышёву от `originPos`. Направление выбирается случайно через seeded RNG среди допустимых клеток. Если допустимой клетки нет, цыплёнок остаётся на месте. Яйцо неподвижно.

При переходах `young → adult` и `adult → old` счётчик `movementClock` сбрасывается, поэтому первый ход цыплёнка происходит через 3 тика после вылупления, а первый ход курицы — через 2 тика после взросления.

Взрослая курица не ограничена радиусом относительно `originPos`. Возможность движения проверяется раз в 2 тика; на таком тике применяется следующий приоритет:

1. При расстоянии до ближайшей головы `≤ adultThreatRadius` (по умолчанию 5) включается активное бегство: цель-яблоко временно игнорируется, а курица выбирает ход, максимально увеличивающий расстояние до ближайшей змейки.
2. В остальных случаях безопасность имеет приоритет над приближением к яблоку. Курица стремится сохранять расстояние не меньше `adultSafetyRadius` (по умолчанию 10) до ближайшей головы. Если она уже находится на расстоянии `6..9`, рассматриваются прежде всего ходы, которые не уменьшают текущую дистанцию. Если безопасного хода нет, выбирается ход с максимально возможным расстоянием до ближайшей головы.
3. Если в радиусе `overcrowdingRadius` (по умолчанию 10) есть другая куриная еда любой стадии — яйцо, цыплёнок или курица, — включается уход из перенаселённой области. Среди безопасных относительно змеек клеток минимизируется количество куриной еды в этом радиусе, затем максимизируется расстояние до ближайшего куриного объекта. Если улучшить положение невозможно, курица выбирает лучший доступный ход внутри поля либо остаётся на месте.
4. Если перенаселения нет и на поле есть яблоки, среди прошедших проверку безопасности клеток выбирается клетка с минимальным расстоянием Чебышёва до ближайшего яблока. Поэтому курица движется в сторону яблок, даже когда они не находятся рядом. Если выбранная клетка занята яблоком, курица переходит на неё и съедает яблоко.
5. Если яблок на поле нет, для каждой допустимой соседней клетки считается число голов живых змеек в радиусе `adultThreatRadius`. Выбирается клетка с минимальным числом змеек. При равенстве выбирается клетка с максимальным расстоянием до ближайшей головы, затем используется seeded RNG.
6. Если нет ни яблок, ни живых змеек, курица случайно выбирает допустимую соседнюю клетку через seeded RNG. Если допустимых клеток нет, она остаётся на месте.

Яйцо, цыплёнок и курица никогда не выходят за границу поля. Обычное движение также не может закончиться на стене, змейке либо другой еде. Единственное исключение по занятости клетки: взрослая курица может перейти на яблоко и удалить его без начисления кому-либо очков или роста.

После поедания яблока курица:

- получает `age = max(foodAdultAge, age − appleAgeReduction)`, по умолчанию возраст уменьшается на 10, но не ниже начала взрослой стадии `age = 100`;
- получает `reproductionCount = max(0, reproductionCount − appleReproductionReduction)`, по умолчанию счётчик уменьшается на 1, но не ниже 0;
- не получает обязательную кладку и не влияет на вероятность следующей обычной кладки.

На каждом тике взрослой стадии курица независимо проверяет возможность кладки с одинаковой вероятностью:

```text
eggLayingProbability = 3 / 50 = 0.06
```

Таким образом, за 50 ходов математическое ожидание числа успешных вероятностных проверок равно трём, а шанс равномерно распределён по всем ходам. Фактическая кладка по-прежнему ограничена `maxEggs = 3`, свободной позицией, `foodMinDistance`, `maxReproductionNeighbors` и общим лимитом всей еды из раздела 6.8. Проверка выполняется через seeded RNG, поэтому одинаковый seed даёт одинаковый результат. Заблокированный ход не переносит вероятность на будущее: на следующем подходящем тике выполняется новая независимая проверка.

Для `ChickenFood` условие фазы базового размножения переопределяется: яйца откладывает только курица в фазе `old`; цыплёнок в фазе `adult` не размножается. Успешная кладка увеличивает `reproductionCount`; `clockNum` не управляет вероятностной кладкой.

Перемещение нескольких объектов еды обрабатывается в стабильном порядке по `id`. Уже выбранная другой едой целевая клетка резервируется до конца тика. Это исключает наложение двух сущностей и сохраняет детерминизм при одинаковом seed.

Значения хранятся в секции `chicken` файла `gameDefaults.json`, а не в коде: `spawnStartLevel = 2`, `spawnProbability = 0.3`, `chickRoamRadius = 5`, `chickMoveInterval = 3`, `adultThreatRadius = 5`, `adultSafetyRadius = 10`, `adultMoveInterval = 2`, `overcrowdingRadius = 10`, `eggLayingProbability = 0.06`, `appleAgeReduction = 10`, `appleReproductionReduction = 1`, `maxEggs = 3`, а также значения очков и роста `1/2/3` по стадиям. Поля `eggLayingInterval = 17` и `reproductionLimitBase = 10` временно сохраняются только для обратной совместимости старых JSON-конфигураций и движком не используются.

### 6.7 Мясо (`MeatFood`)

`MeatFood` отображается значком мяса на косточке 🍖, не двигается, не размножается и имеет только одну стадию:

| Фаза | Возраст | Значок | Очки | Рост |
|------|---------|--------|-----:|-----:|
| `young` | `0..49` | 🍖 | `+1` | `+1` |

На тике, когда `age >= 50`, мясо удаляется. Оно не участвует в обычном начальном спавне, автодобавлении и вероятности появления куриной еды. Поедание мяса змейкой работает как для любой еды: мясо удаляется, змейка получает `+1` очко, растёт на один сегмент и сбрасывает голод.

Мясо создаётся двумя способами:

1. Когда курица достигает `age = 150`, вместо обычного удаления на её текущей клетке создаётся один `MeatFood` с `age = 0`. Съеденная змейкой курица мясо не оставляет.
2. Когда змейка погибает от стены, самоукуса или столкновения с другой змейкой, однократно создаётся `ceil(segments.length / 3)` кусков мяса. Смерть с причиной `'Умерла с голоду'` мяса не создаёт.

Тело погибшей змейки делится от головы к хвосту на последовательные группы максимум по три сегмента. Для каждой группы мясо создаётся на первой входящей в поле уникальной клетке, не занятой стеной или другой едой; если первая клетка непригодна, проверяются следующие клетки группы. Если вся группа занята из-за самопересечения, выбирается ближайшая свободная клетка другого сегмента тела, затем ближайшая свободная клетка рядом с телом со стабильным tie-break по `y`, затем `x`. В нормальном состоянии всегда создаётся ровно `ceil(length / 3)` кусков; меньшее количество разрешено только если на поле физически нет нужного числа свободных клеток.

Серое тело змейки сохраняется до конца раунда по общему правилу, но мясо на его клетках отображается поверх него и имеет приоритет в derived `board[][]`. Поскольку мёртвое тело не участвует в коллизиях, другая змейка может войти в такую клетку и съесть мясо. Создание выполняется только в ответ на событие смерти текущего тика и не повторяется на следующих тиках.

Значения `maxAge = 50`, `scoreValue = 1` и `growthValue = 1` хранятся в секции `meat` файла `gameDefaults.json`.

### 6.8 Размножение еды (общее правило)

Размножение проверяется каждый тик для каждой еды.
`MeatFood` полностью отключает это поведение, а `ChickenFood` переопределяет размножающуюся фазу и ограничения плотности согласно разделу 6.6.
Условия базового алгоритма:
1. Фаза `adult`.
2. `clockNum >= reproductionMinCooldown` (по умолчанию `5`).
3. `reproductionCount < maxReproductions` (по умолчанию `5`).
4. Если соседей в радиусе `neighborReproductionRadius` (Чебышёв) не меньше `maxReproductionNeighbors` (по умолчанию `4`) — размножение блокируется.
5. Любое обычное размножение блокируется, если общее количество всех объектов `Food` достигло общего лимита:

```text
foodReproductionLimit = reproductionLimitBase + snakeCount − difficultyLevel
```

По умолчанию `reproductionLimitBase = 13`. В подсчёт входят яблоки, яйца, цыплята, взрослые курицы, мясо и совместимые расширения еды. Если еды на одну меньше лимита, одно успешное размножение может довести количество ровно до лимита; при равенстве лимиту дальнейшее размножение яблок и кладка куриц блокируются. Уже существующая еда не удаляется.

Параметр хранится как `food.reproductionLimitBase` и доступен в runtime как `foodReproductionLimitBase`. Старый ключ `food.appleReproductionLimitBase` временно сохраняется только для импорта и экспорта совместимых конфигураций и движком не используется.

Вероятность:

```
baseProbability = reproductionProbabilityBase × clockNum
penalty = neighborReproductionPenalty × nearbyCount
probability = baseProbability × (1 − penalty)
```

При успешной проверке создаётся потомок того же типа на расстоянии 1–2 по Чебышёву при соблюдении стандартной валидации клетки.

### 6.9 Автодобавление взрослой еды

Если на поле еды меньше, чем живых змеек, выполняется автодобавление:
1. Добавляется **одна** еда: яблоко создаётся в фазе `adult`, а выбранный по правилу уровня `ChickenFood` всегда создаётся яйцом с `age = 0`.
2. Позиция выбирается как максимально удалённая от голов живых змеек:
   - оптимизируется минимум из дистанций Чебышёва до каждой головы (maximin);
   - при равенстве выбирается позиция с наименьшей разницей дистанций до голов (наиболее равноудалённая);
   - если равенство сохраняется — используется детерминированный tie-break (например, лексикографически по `y`, затем `x`).
3. Ограничение частоты: не чаще 1 раза за `hungerThreshold` тиков.

### 6.10 Гарантированный периодический спавн

На каждом тике, кратном `foodPeriodicSpawnInterval` (по умолчанию 100), гарантированно создаётся одна новая еда независимо от уже находящегося на поле количества еды и общего лимита размножения. Физическое исключение — отсутствие свободной клетки. Позиция выбирается по тому же maximin-правилу удаления от живых змеек, что и для автодобавления. Периодическая еда всегда создаётся новорождённой: яблоко с `age = 0` либо курица в стадии яйца.

На уровне 1 периодически создаётся только яблоко. Начиная с уровня 2 вероятность курицы зависит от количества яблок. Пусть:

- `A` — текущее количество объектов `AppleFood`;
- `S` — количество живых змеек;
- `H = min(2 × S, 10) + 1` — первое целое число яблок, которое больше удвоенного количества змеек либо больше 10.

Тогда:

```text
P(chicken) = 0.30,                                      если A < H
P(chicken) = 0.60 + 0.40 × (A − H) / (20 − H),         если H ≤ A ≤ 20
P(chicken) = 1.00,                                      если A > 20
P(apple)   = 1 − P(chicken)
```

Таким образом, при первом превышении порога вероятность курицы равна 60%, затем линейно растёт и при `A = 20` достигает 100%; при количестве яблок больше 20 курица появляется всегда. Все броски выполняются через seeded RNG. Периодический спавн не отменяет аварийное автодобавление из раздела 6.9, поэтому при малом количестве еды оба правила могут сработать на одном тике.

## 7. Генерация стен

### Параметры генерации

Количество кластеров и длина стен определяются формулами:

```
clusterCount = Math.floor(wallClusterCoeff × level + wallClusterBase)
wallLength   = Math.floor(wallLengthCoeff × difficultyLevel + wallLengthBase)
```

Значения по умолчанию: `wallClusterCoeff = 1.2`, `wallClusterBase = 2`, `wallLengthCoeff = 1.2`, `wallLengthBase = 3`.

Пример: уровень 3, сложность 5 → кластеров = `Math.floor(1.2 × 3 + 2) = 5`, длина = `Math.floor(1.2 × 5 + 3) = 9`.

### Алгоритм генерации (Random Walk + ветвления)

Для каждого кластера:

1. Выбирается **случайная стартовая точка** внутри поля (минимум 2 клетки от края).
2. От стартовой точки выполняется **случайное блуждание** (random walk): на каждом шаге случайно выбирается одно из 4 направлений (вверх/вниз/влево/вправо).
3. С вероятностью **30%** на каждом шаге создаётся **ответвление** — дополнительная стена в случайном направлении от текущей позиции.
4. Каждый новый сегмент проверяется:
   - Он не за пределами поля (не менее 1 клетки от границы).
   - Он не в **зоне безопасности** стартовых позиций змеек.
5. Если нет допустимых направлений — кластер обрывается.

### Зона безопасности змеек

Стены не могут генерироваться рядом со стартовыми позициями змеек.

**Радиус безопасности**: `Math.ceil(1.5 × initialSnakeLength)` клеток (по расстоянию Чебышёва).

При `initialSnakeLength = 5` → радиус = **8 клеток**. Стены не могут быть ближе 8 клеток (по Чебышёву) к любому сегменту стартового тела любой змейки.

Стартовые позиции змеек вычисляются **до** генерации стен. Зоны безопасности строятся по **всем** клеткам, которые будут заняты телами змеек при старте.

### Валидация стен (BFS-связность)

После генерации всех кластеров проверяется связность свободного пространства:

1. Находится **любая** свободная клетка на поле.
2. Запускается **BFS** (поиск в ширину) по свободным клеткам (4 направления: вверх/вниз/влево/вправо).
3. Подсчитывается количество достижимых клеток.
4. Если `visited.size === totalFree` (где `totalFree = width × height − wallCount`) → стены **валидны**.
5. Если нет → стены **невалидны** (есть изолированные зоны), нужна перегенерация.

**Правило**: стены не должны создавать изолированных комнат. Все свободные клетки поля должны быть связаны (достижимы друг из друга).

### Перегенерация

- Если валидация не прошла → генерируется новый набор стен.
- Максимум **50 попыток**.
- Если за 50 попыток не удалось сгенерировать валидные стены → поле создаётся **без стен** (fallback).

### Per-level overrides (dev mode)

В dev-режиме для конкретного уровня можно задать фиксированные значения `wallClusters` и `wallLength`, которые будут использоваться вместо формул.

### Визуальное отображение стен

- Каждая стена занимает одну клетку.
- Заливка: `colorWall` (по умолчанию `#CCCCCC` — светло-серый).
- Без обводки.
## 8. Победа, уровни, счёт

### Общая структура

Игра состоит из **уровней** (level). На каждом уровне:
1. Генерируется новое поле (стены, еда, стартовые позиции).
2. Очки (`score`) и победы (`levelsWon`) **переносятся** между уровнями.
3. Тик уровня (`tickCount`) и таймер (`levelTimeLeft`) — **обнуляются**.
4. После завершения каждого раунда в истории текущей игровой сессии сохраняется снимок результатов всех змеек: число съеденных объектов еды, полученные за раунд и накопленные очки, статус жизни и причина смерти. История переносится между уровнями и очищается только при старте новой игры.

### Бонус за выживание

После штатного завершения каждого раунда каждой змейке, которая осталась живой, **один раз** начисляется бонус, равный её текущей длине:

```text
survivalBonus = snake.alive ? snake.segments.length : 0
snake.score += survivalBonus
```

- бонус начисляется после определения завершения раунда и живых змеек, но до сохранения `roundResults` и показа результатов;
- погибшие змейки бонус не получают;
- если раунд завершился по таймеру и живы несколько змеек, бонус получает каждая из них;
- бонус входит в `scoreGained` текущего раунда и в накопительный `score`, переносимый на следующие уровни;
- начисление выполняется ровно один раз, включая быстрое доигрывание и последний раунд;
- бонус не используется для повторной проверки условия завершения уже закончившегося раунда.

Пример: если за еду в текущем раунде змейка получила 10 очков и завершила раунд живой с длиной 14, её результат за раунд составляет 24 очка: `10 + 14`. Если до раунда у неё уже были накопленные очки, эти 24 очка прибавляются к накопительному значению.

### Одиночная игра (1 змейка)

#### Цель уровня

Формула цели для отдельного уровня (в очках):

```
targetScore(level) = Math.floor(targetScoreCoeff × level + targetScoreBase)
```

По умолчанию: `targetScoreCoeff = 5`, `targetScoreBase = 20`.

**Кумулятивная цель** — сумма целей всех пройденных уровней:

```
cumulativeTarget(level) = Σ targetScore(l) для l = 1..level
```

Примеры (при дефолтных коэффициентах):
- Уровень 1: цель = 25, кумулятивная = 25
- Уровень 2: цель = 30, кумулятивная = 55
- Уровень 3: цель = 35, кумулятивная = 90

#### Условия завершения уровня (классика, 1 игрок)

| Условие | Результат |
|---------|-----------|
| `snake.score >= cumulativeTarget(level)` | **Уровень пройден** — переход к следующему |
| `snake.alive === false` | **Игра окончена** (game over) |

При успешном прохождении:
1. Игра **останавливается** (game loop стоит).
2. Появляется модальное окно «Уровень N завершён» с промежуточными результатами.
3. Игрок нажимает «Продолжить» (или Space) → инициализируется следующий уровень.
4. После завершения уровня 10 игра считается завершённой.

#### Условия завершения уровня (выживание, 1 игрок)

Используются те же базовые правила жизни/смерти змейки и та же формула целевого счёта уровня (`targetScore` / `cumulativeTarget`).

Правила прогрессии:
1. При достижении цели текущего уровня уровень повышается немедленно.
2. Переход выполняется без остановки игры: без модалки и без паузы между уровнями.
3. До уровня 10 активное поле расширяется симметрично с четырёх сторон. Существующие змейка с её длиной и голодом, еда с возрастом и счётчиками, мясо, стены, `tickCount`, идентификаторы еды и прочее состояние сохраняются. Координаты существующих сущностей сдвигаются только для компенсации новой левой и верхней границы, поэтому на экране они остаются на прежнем месте.
4. В открывшейся полосе генерируются дополнительные стены текущего уровня в количестве новых кластеров, заданном разницей формулы стен между уровнями. Поскольку стандартное расширение добавляет по одной клетке с каждой стороны, генератору этого перехода разрешено размещать препятствия на новых крайних клетках; обычная начальная генерация по-прежнему не начинает кластеры на краю. Новая стена не может занять клетку змейки, еды или существующей стены, не создаётся в радиусе безопасности `ceil(1.5 × initialSnakeLength)` от этих сущностей и принимается только при сохранении связности всех свободных клеток. Старые стены не перестраиваются.
5. Начиная с уровня 10 размер поля остаётся максимальным, а дальнейшие уровни до 100 продолжаются на той же доске.
6. После успешного завершения уровня 100 игра завершается победой игрока.

### Многопользовательская игра (≥2 змеек)

#### Условия завершения уровня

| Условие | Результат |
|---------|-----------|
| Осталась **1 живая** змейка | Она — **победитель** уровня, получает `levelsWon++` |
| **Все погибли** | **Нет победителя** (0 побед) |
| Таймер истёк (**3 минуты**), ≥2 живых | **Ничья** (никто не получает побед) |

#### Быстрое доигрывание смешанной игры

Если в раунде участвуют люди и боты, после смерти всех человеческих игроков в левой панели HUD появляется кнопка **«Быстро доиграть»**:

- при одном человеке — после смерти его змейки;
- при двух людях — только после смерти обеих человеческих змеек;
- кнопка показывается, пока хотя бы один бот жив и раунд ещё продолжается;
- кнопка отображается зелёной в основном активном стиле, при появлении получает клавиатурный фокус и запускается клавишей `Enter`;
- игроки могут не нажимать кнопку и досмотреть игру ботов;
- после нажатия обычные интервалы тика и таймера останавливаются;
- текущая партия продолжается теми же ботами, из того же состояния и с тем же RNG;
- Engine рассчитывает ходы пакетами, периодически возвращая управление браузеру;
- перед каждым повышением сложности, то есть раз в секунду реального расчёта, отображается промежуточное состояние Canvas и HUD;
- таймер уровня продвигается по смоделированному времени: каждый рассчитанный тик добавляет `tickIntervalMs`;
- после одной секунды реального расчёта `difficultyLevel` увеличивается на 1 за каждую следующую секунду, но не выше 10;
- расчёт продолжается до штатного завершения текущего раунда: остаётся не более одной живой змейки либо истекает таймер;
- победы, очки и причины смерти формируются обычными системами Engine;
- после последнего тика обязательно отображается финальное состояние поля с местами гибели ботов; через одну секунду открывается штатная модалка завершения текущего уровня;
- быстрое доигрывание не завершает всю игровую сессию: игрок может перейти на следующий уровень; итоговый экран показывается только по обычным условиям game over или после последнего уровня;
- в режиме наблюдателя без людей кнопка не показывается.

#### Таймер уровня

- При инициализации уровня: `levelTimeLeft = levelTimeLimit` (по умолчанию **180** секунд = 3 минуты).
- Каждую секунду: `levelTimeLeft--`.
- При `levelTimeLeft <= 0` → уровень заканчивается.
- Во время паузы таймер **не идёт**.

### Определение итогового победителя

По окончании всех уровней (или при game over) определяется итоговый победитель по приоритету:

1. **Больше побед** (`levelsWon`) → победитель.
2. Если побед **поровну** → у кого **больше очков** (`score`) → победитель.
3. Если и побед, и очков поровну → **ничья** (нет победителя).

### Переход между уровнями

При переходе на следующий уровень:
- `level++`
- `score`, `levelsWon` — **сохраняются** от предыдущего уровня.
- история завершённых раундов (`roundResults`) — **сохраняется** от предыдущего уровня.
- `tickCount = 0`, `levelTimeLeft = levelTimeLimit`.
- Генерируются новые стены, еда, стартовые позиции.
- Все змейки **оживают** (`alive = true`, `deathReason` очищается).
- Длина змеек сбрасывается до `initialSnakeLength`.
- `ticksWithoutFood = 0`.

## 9. Боты (AI)

### Общая концепция

Боты — автономные змейки, управляемые эвристическим алгоритмом. Каждый тик бот анализирует видимую область вокруг головы и выбирает одно из трёх действий: повернуть влево, повернуть вправо или продолжить прямо.

### Интерфейс production-алгоритма

```typescript
interface HeuristicAlgorithm {
  id: string;
  name: string;
  chooseDirection(
    state: GameState,
    snake: Snake,
    settings: GameSettings,
    rng?: RandomPort
  ): Direction;
}
```

Production-бот анализирует полное состояние поля и сразу возвращает абсолютный `Direction`. Сложность выбирает профиль эвристики (`rookie`, `basic`, `solid`, `wise`).

### Ошибки ботов

После расчёта оптимального действия production-бот выполняет отдельную проверку ошибки. Проверка происходит **на каждом тике принятия решения** и использует переданный `RandomPort`; прямой `Math.random()` и привязка ошибки к номеру тика запрещены.

Вероятность ошибки задаётся параметром профиля `mistakePeriod`:

```text
mistakeProbability = mistakePeriod > 0 ? 1 / mistakePeriod : 0
makeMistake = rng.next() < mistakeProbability
```

Целевые значения по умолчанию:

| Сложность | Профиль | `mistakePeriod` | Шанс ошибки на решение |
|---:|---|---:|---:|
| 1–3 | `rookie` | 7 | ≈ 14,3% |
| 4–6 | `basic` | 11 | ≈ 9,1% |
| 7–8 | `solid` | 19 | ≈ 5,3% |
| 9–10 | `wise` | 100 | 1% |

При срабатывании ошибки равновероятно (50/50) выбирается один из двух вариантов:

1. **Повернуть не туда** — вместо рассчитанного абсолютного направления случайно выбирается одно из остальных трёх направлений. В выбор входят опасное направление, продолжение движения прямо и запрещённый разворот на 180°. Ошибочная команда не проходит дополнительную защиту эвристики; запрещённый разворот отклоняется общей проверкой Engine.
2. **Нажать правильный поворот с задержкой** — в текущем тике команда не подаётся, змейка продолжает движение прямо, а рассчитанное правильное направление сохраняется и подаётся на следующем тике.

На тике применения задержанной команды бот не рассчитывает новое направление и не выполняет новую проверку ошибки: сначала подаётся сохранённая команда, затем Engine обрабатывает обычный ход. Задержанная команда не перезаписывается другой командой; после подачи или смерти змейки она удаляется. Если за один тик ситуация изменилась, сохранённый поворот всё равно подаётся и может стать неудачным либо запрещённым относительно текущего направления.

Ошибочное действие может вести в стену, тело змейки, опасную клетку или тупик. Именно поэтому бот способен повернуть не туда либо опоздать с правильным поворотом и погибнуть подобно человеку. Общие правила Engine при этом не обходятся, а смерть определяется штатной системой коллизий.

Дополнительные правила:

- чем выше сложность, тем меньше вероятность ошибки; даже профиль `wise` имеет редкий шанс ошибки;
- `badMoveBias` относится только к текущей частичной реализации и не участвует в новой модели случайной команды; вопрос его последующего удаления решается при рефакторинге реализации;
- один и тот же seed, состояние и последовательность команд должны создавать одинаковую последовательность ошибок;
- быстрое доигрывание не сбрасывает RNG и не отключает ошибки;
- серверные боты используют серверный RNG, а клиент не рассчитывает их ошибки самостоятельно;
- headless Arena и будущая генетическая тренировка явно фиксируют режим ошибок в конфигурации прогона; для сравнения чистого качества алгоритмов ошибки можно отключить, а для оценки устойчивости — оставить включёнными.

Текущее состояние реализации частичное: профили уже содержат `mistakePeriod` и `badMoveBias`, но ошибка привязана к номеру тика, выбирает только несмертельное направление, не поддерживает задержанную команду и отсутствует у `wise`. При реализации нового правила значение `wise.mistakePeriod` в `gameDefaults.json` меняется с `0` на `100`.

Для нейросетевых экспериментов сохраняется observation-интерфейс `BotInput` и относительное решение `BotDecision`:

- `BotInput` содержит повёрнутую `vision`, длину змейки и число тиков без еды;
- `'front'` — продолжить в текущем направлении.
- `'left'` — повернуть налево (например, если змейка шла вправо → пойдёт вверх).
- `'right'` — повернуть направо.

Нейросетевое решение конвертируется в абсолютный `Direction` (`up/down/left/right`) через `getBotDirection`.

### Матрица vision

#### Размер

Квадратная матрица `visionSize × visionSize` (по умолчанию **20×20**).

#### Ориентация

Матрица **повёрнута** относительно текущего направления змейки так, что:
- **Направление змейки** всегда смотрит «вверх» (к row 0).
- Голова змейки находится в **центре** матрицы (`visionSize/2, visionSize/2`).

Утилита `rotateToWorld` переводит координаты матрицы обратно в мировые координаты.

#### Значения ячеек

Ячейки матрицы содержат **суммированные сигналы** от всех ближайших объектов:

**Сигналы препятствий** (стены, границы поля, тела змеек) — **отрицательные**:

| Расстояние (Чебышёв) | Сигнал |
|---|---|
| 1 клетка | `obstacleSignalClose` (по умолчанию **−100**) |
| 2 клетки | −80 |
| 3 клетки | −60 |
| d клеток | `obstacleSignalClose + obstacleSignalDecay × (d − 1)` |

Затухание: `obstacleSignalDecay = 20` за каждую клетку расстояния. Сигналы от нескольких препятствий **суммируются**.

**Сигналы еды** — **положительные**:

| Расстояние (Чебышёв) | Сигнал |
|---|---|
| 1 клетка | `foodSignalClose` (по умолчанию **+100**) |
| 2 клетки | +80 |
| d клеток | `max(foodSignalClose − foodSignalDecay × (d − 1), foodSignalMin)` |
| Минимум | `foodSignalMin` (по умолчанию **+5**), на любом расстоянии |

### Эвристический алгоритм

Базовый алгоритм этапа 7 — **жадный full-board heuristic**:

1. На каждом тике бот оценивает все допустимые абсолютные направления (`up/down/left/right`, кроме разворота на 180°).
2. Для каждого кандидата выполняется проверка немедленной смерти (граница, стена, живая змейка).
3. Для безопасного кандидата считается flood-fill по всей доске (доступная площадь после шага) и штраф тупика.
4. Параллельно оценивается жадная ценность еды:
   - приоритет ближайшей еды;
   - при равной дистанции выше приоритет у еды с большей ценностью очков (`&xN`).
5. Итоговая оценка хода комбинирует:
   - доступную площадь и локальные пути отхода;
   - бонус за еду;
   - штраф за риск входа в узкие области.

Выбирается ход с максимальной итоговой оценкой.

### Тестовая арена ИИ

Headless-модуль арены находится в `packages/core/src/arena/` и поддерживает любые алгоритмы (в т.ч. нейросетевые) через интерфейс `ArenaAlgorithm`. Визуальный `ArenaDemoRunner` остаётся в браузерном слое `src/arena/`.

1. **Headless arena** (без canvas):
   - класс `Arena` — симуляция до смерти, завершения уровня или `maxTicks`;
   - `runOne(maxTicks?)` возвращает фитнес: score, survivedTicks, survivedMs, aliveAtEnd, deathReason;
   - `runArenaSimulation(config)` / `runArenaBatch(config)` — одиночный и пакетный прогоны.
   - seeded RNG передаётся не только Engine, но и алгоритмам участников; одинаковые конфигурация и seed должны давать одинаковый результат, включая случайную и нейросетевую политики.
2. **Сравнение алгоритмов**:
   - разные алгоритмы назначаются разным змейкам через `participants`;
   - агрегируются средние показатели по каждому алгоритму.
3. **Demo arena** (с рендером):
   - класс `ArenaDemoRunner`, фабрика `createArenaDemoController(options)`;
   - визуальный запуск на canvas, ускорение `1x / 2x / 4x / 8x`.
## 10. Интерфейс и экраны

Весь интерфейс на **русском языке**. Стили — через CSS-классы и CSS custom properties (никаких inline-стилей).

Приложение состоит из 3 основных экранов: **Меню**, **Игра**, **Результаты**. Переключение между экранами через простой JS-роутер (перерисовка содержимого `#app`).

### 10.1 Экран «Меню»

Отображается при загрузке страницы и при возврате из экрана результатов.

#### Содержимое

1. **Заголовок**: `Голодные змейки 🐍`
2. **Панель настроек** (визуально выделенная карточка), содержащая:

| Поле | Тип | Диапазон | Значение по умолчанию |
|------|-----|----------|----------------------|
| Игроки (0–2) | `<input type="number">` | 0–2 | 1 |
| Боты (0–4) | `<input type="number">` | 0–4 | 0 |
| Имя игрока 1 | `<input type="text">` + кнопка ▼ | — | `Игрок 1` |
| Имя игрока 2 | `<input type="text">` + кнопка ▼ | — | `Игрок 2` |
| Сложность (1–10) | `<input type="number">` | 1–10 | 1 |

3. **Кнопка «СТАРТ»** — по центру, начинает игру.
4. **Кнопка «🛠 Режим настройки»** — появляется **только в dev-сборке** (`__DEV_MODE__ === true`). Запускает игру с dev-панелью.

#### Вёрстка меню

- Форма — grid-раскладка в 2 столбца: метки слева, поля ввода справа.
- Поля ввода **выровнены по правому краю**.
- Кнопка «СТАРТ» — на отдельной строке, по центру.

#### Dropdown имён

Рядом с каждым полем «Имя игрока» есть кнопка **▼**. При клике:
- Открывается выпадающий список с ранее сохранёнными именами (из `localStorage`).
- При выборе имени — оно подставляется в поле.
- Если сохранённых имён нет — отображается «Нет сохранённых имён».
- Кликнуть за пределами списка — закрыть его.

При нажатии «СТАРТ» имена активных игроков сохраняются в `localStorage`.

#### Валидация при старте

- `playerCount` обрезается до `[0, 2]`.
- `botCount` обрезается до `[0, 4]`.
- `difficultyLevel` обрезается до `[1, 10]`.

### 10.2 Экран «Игра»

#### DOM-структура (обычный режим)

```
#app
  .game-outer
    #game-area (.game-area, position: relative)
      .game-top-bar         ← верхняя панель (HUD)
      .game-middle           ← flex-строка: игроки + canvas + боты
        .game-players-panel       ← вертикальная колонка слева
          «Игрок 1» + #hud-left  ← статистика Игрока 1
          «Игрок 2» + #hud-right ← статистика Игрока 2
          #hud-fast-forward       ← кнопка под обоими HUD игроков
        canvas#gameCanvas         ← игровое поле
        .game-bots-panel          ← вертикальная колонка ботов справа
          «Боты» + #hud-bottom   ← карточки всех ботов
      #touch-controls-single ← touch-кнопки (только для 1P на touch-устройствах)
      #modal-overlay         ← (при паузе/конце уровня — поверх game-area)
```

#### DOM-структура (dev-режим)

```
#app
  .game-outer
    .game-layout-row         ← flex-строка: game-area + dev-панель
      #game-area (.game-area)
        .game-top-bar
        .game-middle .game-middle--dev
          .game-players-panel
          canvas#gameCanvas
          .game-bots-panel
        #modal-overlay       ← покрывает ТОЛЬКО game-area, не dev-панель
      #dev-panel-container   ← панель настроек (вне game-area, всегда доступна)
```

**Важно**: модальные окна (пауза, конец уровня, game over) вставляются внутрь `#game-area` с `position: absolute`, а не в `document.body`. Это гарантирует, что overlay покрывает **только игровую область**, но не dev-панель.

#### Верхняя панель (HUD top bar)

Горизонтальная строка над игровым полем. Содержит:

| Элемент | Описание |
|---------|----------|
| `Уровень: N` | Текущий номер уровня |
| `Цель: X` | Кумулятивная цель по очкам (для одиночной игры) |
| `Время: M:SS` | Оставшееся время уровня (в многопользовательской) |
| `Тик: N` | Текущий номер тика |
| Подсказка | `Пробел — пауза` (или мигающее `⏸ ПАУЗА` если стоит на паузе) |

#### Левая колонка игроков

Расположена **слева** от canvas. Содержит два вертикально расположенных блока:

1. Заголовок `Игрок 1`, под ним HUD первого человека.
2. Ниже заголовок `Игрок 2`, под ним HUD второго человека.

Каждый HUD содержит:

```
Имя (bold)
Очки: N
Длина: N
Победы: N
Статус: Жив / [причина смерти]
```

Если соответствующего игрока нет, его секция скрывается целиком: заголовок, HUD и пустое место не показываются. Если людей нет, вся левая колонка скрыта.

В смешанной игре после смерти всех человеческих игроков кнопка **«Быстро доиграть»** появляется в левой колонке **ниже всех существующих HUD игроков**, а не внутри карточки Игрока 1. Остальные правила быстрого доигрывания раунда не меняются.

#### Правая колонка ботов

Расположена **справа** от canvas. Под заголовком `Боты` вертикально выводится по одной карточке на каждого бота. Каждая карточка содержит ту же статистику (имя, очки, длина, победы, статус).

Если ботов нет — панель пуста.

#### Цвет статистики змеек

- Весь информационный блок змейки — имя, очки, длина, победы и статус — отображается цветом этой змейки из `snakeColors`.
- После смерти весь информационный блок становится того же серого оттенка, которым на Canvas отображается тело мёртвой змейки.
- Правило одинаково для человеческих игроков и ботов.

#### Размер canvas

Canvas подстраивается под доступное пространство:
- `cellSize = Math.max(2, Math.min(Math.floor(maxW / boardWidth), Math.floor(maxH / boardHeight)))`
- `maxW` и `maxH` вычисляются из размера окна, за вычетом боковых панелей и (в dev-режиме) ширины dev-панели.
- в режиме выживания `boardWidth` и `boardHeight` для расчёта canvas сразу соответствуют максимальному полю уровня `survivalMaxBoardLevel`; активное поле меньших уровней рисуется по центру этого canvas, поэтому переход уровня не меняет размеры bitmap и не вызывает визуального мигания.

#### Маркеры игроков при старте раунда

- В течение первой секунды каждого раунда рядом с головой каждой человеческой змейки отображается круглый пульсирующий маркер с номером игрока: `1` или `2`. Автоматическое повышение уровня в выживании не считается новым раундом и повторно маркер не запускает.
- Маркер расположен со смещением вверх и влево от головы, но всегда остаётся внутри canvas.
- Контур и номер маркера имеют цвет соответствующей змейки. Если змейка успела погибнуть до исчезновения маркера, используется серый цвет мёртвой змейки.
- Для отсутствующего второго игрока маркер `2` не создаётся. Боты стартовыми маркерами не помечаются.

### 10.3 Модальные окна

Все модальные окна реализованы единообразно:
- **Overlay**: полупрозрачный чёрный фон (`rgba(0,0,0,0.75)`) покрывает весь `#game-area`.
- **Контент**: белая карточка по центру overlay.
- **Анимация**: fade-in при появлении.
- Overlay имеет `position: absolute` внутри `#game-area` (не `fixed`).

#### 10.3.1 Модалка «Пауза»

Появляется при нажатии Space во время игры.

Содержимое:
- Заголовок: `⏸ ПАУЗА`
- Подсказка: `Нажмите Пробел или кнопку ниже`
- Кнопка: `▶ Продолжить`

Закрытие (снятие паузы):
- Нажатие Space
- Клик по кнопке «Продолжить»
- Клик по overlay (за пределами карточки)

#### 10.3.2 Модалка «Конец уровня»

Появляется когда уровень завершён в режимах:
- одиночная **классика**;
- многопользовательская/смешанная игра.

В режиме **выживания** эта модалка не показывается: переход между уровнями выполняется автоматически.

Содержимое:
- Заголовок: `Уровень N завершён`
- Подзаголовок: `Цель: X очков`
- Таблица с результатами всех змеек:

| Имя | Очки | Длина | Победы | Статус |
|-----|------|-------|--------|--------|
| ... | ... | ... | ... | Жив / [причина смерти] |

- Кнопка: `▶ Продолжить`
- Подсказка: `или нажмите Пробел`

Закрытие: Space или кнопка → переход к следующему уровню.

В dev-режиме, если это game over, вместо перехода на экран результатов показывается модалка конца уровня (без перехода).

#### 10.3.3 Модалка «Игра окончена»

Появляется при game over (единственная змейка погибла / все уровни пройдены).

Содержимое:
- Заголовок: `Игра окончена` (красным)
- Таблица (как при конце уровня)
- Кнопка: `Результаты`
- Подсказка: `или нажмите Пробел`

Закрытие: Space или кнопка → переход на экран результатов.

---

### 10.4 Экран «Результаты»

Появляется после game over.

Содержимое и порядок блоков сверху вниз:

1. **Заголовок**: `Итоговые результаты`.
2. **Итоговая таблица текущей игры по всем раундам**: место, имя, тип участника (игрок/бот), общее количество съеденной еды, победы, итоговые очки и статус в последнем раунде.
3. **Объявление победителя**:
   - победитель определяется по правилам раздела 8;
   - при полном равенстве побед и очков у лидеров объявляется ничья с перечислением этих участников.
4. **Пьедестал**:
   - слева — меньшее бронзовое третье место;
   - по центру — самое высокое золотое первое место;
   - справа — серебряное второе место;
   - каждое занятое место показывает медаль, место, имя, число побед и итоговые очки;
   - при числе участников меньше трёх незанятые места остаются пустыми, а первое место сохраняет центральное положение.
5. **Таблица рекордов** (из `localStorage`): топ-10 реальных игроков, с полями #, Имя, Очки, Дата. Результаты ботов не сохраняются в таблицу рекордов; ранее сохранённые записи с признаком `isBot` не отображаются.
6. **Кнопки**:
   - `Заново` — перезапуск с текущими настройками.
   - `Меню` — возврат в меню.

Имена игроков и данные из `localStorage` выводятся как текст с HTML-экранированием и не интерпретируются как разметка. Результаты одного и того же состояния завершённой игры сохраняются не более одного раза.

Экран имеет строго вертикальную компоновку. Итоговая таблица, пьедестал и таблица рекордов располагаются последовательно друг под другом и никогда не образуют колонки даже на широком экране. Перед таблицей рекордов предусмотрен заметный вертикальный отступ. Отдельная таблица с построчными результатами каждого раунда не показывается: итоговая таблица содержит агрегированные данные всей игры.

## 12. Режим настройки (dev mode)

### Активация

Dev-режим доступен **только** при сборке с флагом `devmode`:

```bash
npm run dev:debug    # webpack serve --mode development --env devmode --open
```

Webpack определяет глобальную переменную `__DEV_MODE__: boolean` через `DefinePlugin`. В обычной сборке (`npm start`, `npm run build`) переменная равна `false`, и весь код dev-панели не попадает в бандл (tree-shaking).

### Кнопка в меню

В dev-сборке на экране «Меню» появляется дополнительная кнопка **«🛠 Режим настройки»**. При нажатии запускается игра с активным dev-режимом.

### Расположение dev-панели

В dev-режиме игровое поле сдвинуто **влево**, а **справа** от него располагается панель настроек. DOM-структура:

```
.game-layout-row  (flex-строка)
  #game-area      (flex: 1, position: relative — содержит поле, HUD, overlay)
  #dev-panel-container  (фиксированная ширина — содержит панель настроек)
```

**Важно**: dev-панель находится **вне** `#game-area`. Модальные окна (пауза, конец уровня) вставляются внутрь `#game-area` с `position: absolute`. Таким образом, overlay покрывает **только** игровую область, а панель настроек **остаётся кликабельной** во время паузы и модалок.

### Содержимое dev-панели

Панель организована в **секции** (разделы), каждая с заголовком и набором строк «Метка — поле ввода». Все значения привязаны к полям синглтона `gameSettings`.

Для каждого поля (кроме `snakeColors[0..5]`) есть чекбокс **«Для всех уровней»**:
- по умолчанию включён;
- включён → значение считается глобальным (`gameSettings`);
- выключен → значение пишется как per-level override для выбранного уровня (`levelSettingsOverrides[level]`).

Для строк цветов змейки (`snakeColors[0..5]`) чекбокс scope не показывается — эти поля всегда глобальные.

#### 12.1 Секция «Уровень»

| Поле | Описание |
|------|----------|
| Уровень | Номер уровня для перезапуска (input number, min=1) |

При изменении номера уровня панель перерисовывается, подставляя per-level overrides для выбранного уровня.

#### 12.2 Секция «Настройки уровня N» (per-level overrides)

| Поле | Описание |
|------|----------|
| Кластеров стен | Переопределение `wallClusters` для текущего уровня |
| Длина стен | Переопределение `wallLength` |
| Еды (нач.) | Переопределение начального количества еды |

Если override для уровня не задан — подставляются значения из формул (показываются как дефолт).

#### 12.3 Секция «Змейка»

| Поле | Ключ `gameSettings` |
|------|-----|
| Тики голода | `hungerThreshold` |
| Нач. длина | `initialSnakeLength` |
| Мин. длина (смерть) | `minSnakeLength` |

#### 12.4 Секция «Жизненный цикл еды»

| Поле | Ключ |
|------|------|
| Молодость до (тик) | `foodYoungAge` |
| Взрослый до (тик) | `foodAdultAge` |
| Смерть на тике | `foodMaxAge` |

#### 12.5 Секция «Спавн и размножение еды»

| Поле | Ключ |
|------|------|
| Мин. дистанция | `foodMinDistance` |
| Кулдаун размнож. | `reproductionMinCooldown` |
| Вероятность | `reproductionProbabilityBase` (step 0.01) |
| Макс. потомство | `maxReproductions` |
| Радиус соседей | `neighborReproductionRadius` |
| Макс. соседей | `maxReproductionNeighbors` |
| Штраф за соседа | `neighborReproductionPenalty` (step 0.05) |
| База общего лимита еды | `foodReproductionLimitBase` |

#### 12.6 Секция «Генерация еды (формулы)»

| Поле | Ключ |
|------|------|
| Коэфф. на змейку | `foodCountPerSnakeCoeff` (step 0.1) |
| Базовое кол-во | `foodCountBase` |
| Период автоспавна | `foodPeriodicSpawnInterval` |

#### 12.7 Секция «Куриная еда»

| Кнопка | Действие |
|--------|----------|

### Сохранение настроек

- При каждом «Применить» / «Сохр. ур.» текущие `gameSettings` (включая per-level overrides) сохраняются в `localStorage` под ключом `snake-dev-settings`.
- При открытии dev-панели: если в `localStorage` есть сохранённые настройки → они загружаются и применяются к `gameSettings`.
- «Сброс» очищает `localStorage` и возвращает `gameSettings` к дефолтам из `gameDefaults.json`.

Экспортируемый файл имеет **ту же структуру**, что и `gameDefaults.json`:


### Поведение при game over в dev-режиме

При проигрыше в dev-режиме **экран результатов не показывается**. Вместо модалки «Игра окончена» → показывается модалка «Конец уровня», после которой можно продолжить игру (перезапуск того же уровня).

## 13. Конфигурация и параметры

### Единый источник параметров

Все игровые константы хранятся в **одном** JSON-файле:

**`src/gameDefaults.json`**

Этот файл — каноническое хранилище дефолтных значений. Он:
1. Импортируется в `settings.ts` и используется для инициализации `gameSettings`.
2. Может быть заменён файлом, экспортированным из dev-панели.
3. Не содержит кода — только данные.

### Runtime настройки (`gameSettings`)

`gameSettings` — мутабельный базовый объект `GameSettings`, инициализируемый из `gameDefaults.json` при загрузке модуля `settings.ts`.

При создании уровня Engine строит отдельный объект эффективных настроек из `gameSettings` и override текущего уровня. Базовый `gameSettings` при этом не мутируется, поэтому настройки одного уровня не протекают в следующий. Все системы активного уровня читают параметры из этого объекта через `EngineContext`, а не из JSON напрямую.

```typescript
export const gameSettings: GameSettings = createDefaultSettings();
```

Dev-панель может изменять поля `gameSettings` в runtime. Функция `resetSettings()` восстанавливает все поля из `gameDefaults.json`.

### Политика ключей конфигурации

- Актуальными считаются только ключи новой схемы (`food*`, `foodCount`, `foodSignal*`, `colors.food*`).
- Legacy-ключи старой схемы (`rabbit*`, `rabbitCount`, `rabbitSignal*`, `colors.rabbit*`) в актуальном ТЗ не используются.
- И frontend-код, и AI/automation-агенты должны опираться только на актуальные ключи новой схемы.

## 14. Игровой цикл (tick-based)

### Общий принцип

Игра работает на **дискретных тиках**. Каждый тик = один шаг симуляции. Между тиками визуальных изменений нет (нет интерполяции).

**Интервал тика**: `tickIntervalMs` (по умолчанию **150 мс** ≈ 6.67 тиков/сек).

Game loop реализован через `setInterval`. При паузе интервал **очищается**, при возобновлении — создаётся заново.

### Таймер уровня

Отдельный `setInterval(1000 мс)` вызывает команду Engine, уменьшающую `state.levelTimeLeft` на 1. App-слой не изменяет `GameState` напрямую. При паузе этот интервал тоже останавливается.

### Порядок операций в одном тике

Каждый вызов `processTick(state)` выполняет строго в следующем порядке:

```
1. tickCount++

2. Для всех живых змеек одновременно:
   a. Вычислить намерение хода: новую позицию головы, еду и предполагаемый рост
   b. Проверить столкновения со стенами
   c. Разрешить столкновения голов: при ходе нескольких голов в одну клетку или обмене клетками погибают все участвующие змейки
   d. Проверить столкновения с собственным и чужими телами по состоянию после предполагаемого движения; вход в хвост, освобождаемый в этом тике, разрешён
   e. Для выживших применить перемещение
   f. Если змейка ест: удалить еду, увеличить score и сбросить голод

3. Для каждой живой змейки:
   h. processHunger (ticksWithoutFood++, потеря сегмента, возможная смерть)

4. processFoodLifecycle:
   i.  Для всей еды: age++, clockNum++
   j.  Истёкшую курицу заменить мясом; остальную еду с достигнутым `maxAge` удалить
   k.  Для яблок в размножающейся фазе: проверка условий, бросок вероятности, спавн потомка; для каждой взрослой курицы — независимая проверка кладки с вероятностью 0,06 на каждом тике
   l.  На каждом `foodPeriodicSpawnInterval`-м тике гарантированно добавить новорождённую еду с динамической вероятностью курицы
   m.  При дефиците еды выполнить независимое аварийное автодобавление

5. processMovingFood:
   o.  Обновить `movementClock` оставшейся куриной еды
   p.  Для цыплят и куриц с наступившим ходом выбрать и применить допустимое перемещение в стабильном порядке по `id`
   q.  При переходе курицы на яблоко удалить яблоко, уменьшить `age` на 10 с нижней границей 100 и уменьшить `reproductionCount` на 1 с нижней границей 0; `clockNum` не менять

6. processSnakeDeathDrops:
   r.  Для событий смерти от столкновения текущего тика один раз создать мясо по группам сегментов
   s.  Смерть от голода пропустить

7. Пересобрать board[][] из сущностей; мясо имеет приоритет над сегментами мёртвой змейки

8. Проверить checkLevelComplete:
   - Одиночная (классика): score >= cumulativeTarget → levelComplete; !alive ИЛИ успешно завершён уровень 10 → gameOver
   - Одиночная (выживание): score >= cumulativeTarget → мгновенно расширить существующее поле без пересоздания сущностей и без паузы; после уровня 10 сохранить максимальный размер; !alive ИЛИ успешно завершён уровень 100 → gameOver (поражение/победа)
   - Мультиплеер: alive <= 1 ИЛИ timeLeft <= 0 ИЛИ успешно завершён уровень 10 → levelComplete/matchEnd
   - Присвоить levelsWon победителю (мультиплеер)

9. Если раунд завершён, один раз начислить каждой живой змейке бонус `segments.length`, затем зафиксировать `roundResults`.
```

### Обработка ввода (вне processTick)

Направления от игроков и ботов применяются **до** вызова `processTick`:

1. `InputHandler` собирает последовательность нажатий для каждого игрока. На границе тика выбирается последнее направление, которое не является разворотом на 180° относительно текущего направления; более позднее недопустимое нажатие не отменяет предыдущее допустимое.
2. Для production-ботов `processBots()` выбирает профиль по сложности и вызывает full-board heuristic, возвращающую абсолютный `Direction`. Нейросетевые алгоритмы отдельно формируют `BotInput` и преобразуют относительный `BotDecision` через `getBotDirection()`.
3. `applyDirection(snake, direction)` — устанавливает направление (с проверкой запрета 180°).
4. Вызывается `processTick(state)`.

### Рендеринг (вне processTick)

После `processTick`:
1. `renderGame(ctx, state, cellSize, settings, options)` — перерисовка canvas; временные визуальные параметры (например, время стартовых маркеров игроков) передаются через `options` и не входят в состояние Engine.
2. `renderHUD(...)` — обновление панелей статистики.
3. Проверка `state.levelComplete` → если да, показ модалки.

### Жизненный цикл уровня

```
startGame(config, level)
  → createGameState(config, level)
  → initLevel(state, config)
    → getStartPositions → exclusionZones
    → generateWalls (с зонами безопасности)
    → createSnake × N
    → spawnFood
    → buildBoard
  → buildGameDOM
  → startGameLoop
    → setInterval(processTick + render, tickIntervalMs)
    → setInterval(timer, 1000ms)

// На каждый тик:
gameLoopTick()
  if (paused) return
  applyInputs()
  processTick(state)
  renderGame()
  renderHUD()
  if (state.levelComplete) → handleLevelComplete()

handleLevelComplete()
  → stopGameLoop
  → showLevelCompleteModal / showGameOverModal
  → ожидание Space / кнопки

continueAfterLevelEnd()
  → если game over → finishGame → экран результатов
  → иначе → advanceToNextLevel → startGameLoop
```

## 15 Принципы архитектуры (обязательные)

### 15.1 Цели качества

Код проекта должен быть:

1. **Чистый**: понятные имена, короткие функции, минимум дублирования, единый стиль.
2. **Поддерживаемый**: изменения в одной подсистеме не должны требовать правок во многих файлах.
3. **Тестируемый**: ключевая логика engine покрывается unit-тестами без DOM/Canvas; тесты детерминированы.
4. **Расширяемый**: новые механики/сущности/экраны добавляются через новые модули/системы, а не через разрастание условий в центральных файлах.
5. **Читаемый**: управление жизненным циклом игры и UI (экраны/модалки/пауза) описано явно и однозначно, без противоречивых комбинаций флагов.
6. **Слабо связанный**: доменная логика (engine) не импортирует и не использует адаптеры окружения (DOM, Canvas, localStorage, таймеры).

---

### 15.2 Разделение на слои (Layering)

#### Engine (домен)

1. Engine — чистая логика симуляции: состояние, формулы, движение, коллизии, спавн, механики.
2. Engine **не использует**: DOM API, Canvas API, `localStorage`, `setInterval`, прямой `Math.random()`.
3. Engine допускает только:
   - чтение/мутацию `GameState`;
   - генерацию доменных событий (см. 15.6);
   - чтение параметров только из `gameSettings`/`EngineContext`.

#### App/UI (приложение)

1. App/UI отвечает за:
   - роутинг по экранам;
   - обработку пользовательского ввода;
   - показ модалок и управление паузой;
   - запуск/остановку game loop;
   - работу со storage (рекорды, имена, dev-настройки).
2. App/UI **не мутирует** `GameState` напрямую (см. 15.4).

#### Renderer

1. Renderer читает состояние и рисует; **не содержит логики** симуляции и не мутирует `GameState`.
2. Любые визуальные эффекты (если появятся) хранятся в отдельном “visual state” renderer-слоя и **не влияют** на правила игры.

---

### 15.3 Порты и адаптеры (Hexagonal / Ports & Adapters)

1. Все зависимости на окружение оформляются как **порты (интерфейсы)** в Engine и реализуются **адаптерами** в App/Infra.
2. Минимально обязательный порт: `RandomPort` (RNG).
   - Все операции случайности в Engine используют `ctx.rng.next()`.
   - Прямой `Math.random()` в модулях `engine/**` запрещён.
3. Дополнительные порты (рекомендуются): `StoragePort`, `SchedulerPort`/`ClockPort`, `LoggerPort`.

---

### 15.4 Единый источник истины (Single Source of Truth) — вариант A

1. `GameState` — **единственный источник истины** для текущей партии (позиции, очки, возраст, статусы и т.д.).
2. Мутация `GameState` разрешена только:
   - внутри функций Engine (`initLevel`, `processTick`, системы);
   - через единый use-case слой приложения (например `GameController`), который вызывает Engine в правильном порядке.
3. UI/Renderer/InputHandler **не имеют права** мутировать `GameState` напрямую.
4. Производные структуры (`board[][]`, occupancy-кэши и т.п.) должны быть **пересчитываемыми** и не являются мастер-данными.

---

### 15.5 Pipeline / Systems (конвейер систем тика)

1. `processTick` реализуется как последовательность **систем** (pipeline), каждая отвечает за одну механику/фазу.
2. Система имеет единый контракт (рекомендуется): `run(state, ctx, out)` и не взаимодействует с DOM/Canvas.
3. Порядок выполнения систем соответствует регламенту тика из раздела 14 и задаётся явным списком систем.
4. Добавление новых механик выполняется через:
   - добавление новой системы;
   - или расширение одной системы;
   без разрастания монолитной функции.

---

### 15.6 Доменные события (Domain Events)

1. Engine не вызывает UI/звуки/анимации напрямую. Вместо этого Engine формирует **Domain Events** (события фактов).
2. `processTick` возвращает `TickResult { events: DomainEvent[] }` (или эквивалентный механизм), содержащий события тика.
3. Примеры доменных событий (минимальный обязательный набор):
   - `SNAKE_DIED` (snakeId, reason)
   - `FOOD_EATEN` (snakeId, pos, newScore)
   - `FOOD_BORN` (parentPos, childPos)
   - `LEVEL_COMPLETED` (reason, winnerId?)
   - `GAME_OVER` (если применимо)
4. App-слой обрабатывает Domain Events и выполняет побочные эффекты: модалки, звук, storage, переходы экранов.

---

### 15.7 Ввод пользователя: Command Buffer + применение на границе тика

1. Обработчики DOM-событий не меняют `GameState`. Они складывают команды в буфер (`InputBuffer`).
2. На каждом тике команды **потребляются** и применяются строго в начале тика (в соответствии с правилами ввода из раздела 3 и регламентом тика из раздела 14).
3. Буфер ввода должен поддерживать правило: “последнее валидное направление за тик” и запрет разворота на 180°.

---

### 15.8 UI/экраны/пауза: конечный автомат (FSM)

1. Логика экранов и модалок реализуется через **Finite State Machine (FSM)**.
2. `Space` и кнопки работают как события FSM; поведение Space определяется текущим состоянием автомата (раздел 3. Пауза).
3. Противоречивые комбинации флагов (например, “paused=true и одновременно модалка конца уровня”) не допускаются; валидность обеспечивается моделью состояний.
4. Переходы (menu → game → results, playing ↔ paused, levelComplete, gameOver) описываются явно (таблица переходов или reducer-функция).

---

### 15.9 Контекст зависимостей (явная DI без контейнеров)

1. Engine получает зависимости через `EngineContext` (например: `settings`, `rng`, опционально `scratch`).
2. Тесты могут подменять зависимости (seeded RNG, настройки) без моков DOM.

---

### 15.10 Derived-данные и оптимизации

1. `board[][]` и любые occupancy-индексы являются derived-структурами и могут пересобираться из мастер-данных (по ТЗ — каждый тик).
2. Коллизии и правила симуляции должны опираться на мастер-данные (`snakes`, `foods`, `walls`) либо на корректно синхронизированные derived-индексы, построенные из мастер-данных в пределах тика.

---

### 15.11 Обязательные OOP-требования

1. Ключевые доменные сущности реализуются как классы с инкапсулированным поведением (например, `SnakeEntity`, `FoodEntity`), а не как набор разрозненных процедур.
2. Файл `engine/types.ts` содержит только типы/интерфейсы TypeScript. Конкретные реализации классов в него не помещаются.
3. Публичный API классов должен выражать доменные действия (`move`, `applyDirection`, `die`, `tickLifecycle`), а не технические детали хранения.
4. Инварианты сущностей (запрет разворота на 180°, корректная смерть, корректное изменение длины, счётчиков и т.п.) поддерживаются внутри методов классов.
5. Оркестрация use-case уровня (`GameController`, `SnakeGameApplication`) не содержит доменных вычислений сущностей, а координирует вызовы сервисов/engine.
6. Классы должны соответствовать SRP: при росте сложности ответственность выносится в отдельные сервисы/координаторы, а не накапливается в одном «god object».
7. Предпочтение отдаётся композиции над наследованием; наследование допускается только при явной и устойчивой модели «is-a».
8. Зависимости передаются явно (DI через контекст/конструктор); скрытые глобальные зависимости внутри классов не допускаются.

---

### 15.12 Планируемый монорепозиторий, сервер и обучение

1. Следующий крупный этап — сетевой мультиплеер с авторитетным Node.js-сервером и передачей снимков состояния через WebSocket.
2. Генетическое обучение реализуется после мультиплеера, но учитывается при выделении общего environment-independent core.
3. Целевая структура содержит браузерное и серверное приложения, общий пакет Engine/Arena/AI/training и отдельный пакет сериализуемых контрактов.
4. Сервер, браузер, headless Arena и будущее обучение используют одну реализацию Engine.
5. Сетевая комната поддерживает до 6 змеек суммарно, публичный или приватный доступ, серверных ботов и ready-check подключённых игроков.
6. Сервер отправляет авторитетный снимок каждый тик; клиент предсказывает движение собственной змейки и согласует его с подтверждёнными сервером командами.
7. История сетевых матчей сохраняется на сервере через заменяемый repository-порт.
8. Технический результат игрового слота и личные результаты сменявших друг друга человека/бота учитываются раздельно.
9. Подробные принятые решения, открытые вопросы и план этапов зафиксированы в `docs/architecture-roadmap.md`.


## 16. Тесты (Jest)

### Общие требования

- Среда: **jsdom** (для тестов, использующих DOM API).
- CSS-импорты мокаются через `styleMock.js`.
- Все engine-тесты **не зависят** от DOM — тестируют чистую логику.
- Формат: `describe` + `it`/`test`, с понятными описаниями на английском или русском.
- Перед каждым тестом: `resetSettings()` для чистого состояния.

### Обязательные группы тестов (Этап 3c)

#### 16.1 Движение змейки

| Тест | Что проверяется |
|------|-----------------|
| `getNextHeadPosition` вычисляет правильную клетку для каждого направления | `up` → y−1, `down` → y+1, `left` → x−1, `right` → x+1 |
| `moveSnake(grow=false)` добавляет голову и удаляет хвост | Длина не меняется, голова на новой позиции |
| `moveSnake(grow=true)` добавляет голову, хвост остаётся | Длина += 1 |

#### 16.2 Запрет разворота на 180°

| Тест | Что проверяется |
|------|-----------------|
| `isReverseDirection('right', 'left')` → `true` | Противоположные направления определяются |
| `isReverseDirection('right', 'up')` → `false` | Поворот на 90° разрешён |
| `applyDirection` с разворотом не меняет direction | Змейка сохраняет прежнее направление |
| `applyDirection` с поворотом на 90° меняет direction | Направление обновляется |

#### 16.3 Коллизии

| Тест | Что проверяется |
|------|-----------------|
| `collidesWithWall` при выходе за границы → `true` | Позиция `(-1, 5)` или `(width, 0)` |
| `collidesWithWall` при попадании на стену → `true` | Позиция совпадает с элементом `state.walls` |
| `collidesWithWall` на свободной клетке → `false` | |
| `selfCollision` при наличии совпадения головы с сегментом → `true` | |
| `selfCollision` при отсутствии совпадения → `false` | |
| `collidesWithSnake` с другой змейкой → `true` | Позиция совпадает с сегментом другой живой змейки |
| `collidesWithSnake` с мёртвой змейкой → `false` | Мёртвые змейки не учитываются |

#### 16.4 Голод

| Тест | Что проверяется |
|------|-----------------|
| `processHunger` после `hungerThreshold − 1` тиков без еды — змейка цела | `ticksWithoutFood` инкрементируется |
| `processHunger` на тике `hungerThreshold` — теряет 1 сегмент | `segments.length` уменьшается на 1, `ticksWithoutFood = 0` |
| Повторная потеря сегментов до `minSnakeLength` → `alive = false` | `deathReason = 'Умерла с голоду'` |
| `resetHunger` сбрасывает `ticksWithoutFood` в 0 | |

#### 16.5 Поедание еды

| Тест | Что проверяется |
|------|-----------------|
| Змейка съедает еду → `score += food.scoreValue` | |
| Змейка растёт на `food.growthValue` сегментов | `segments.length` увеличивается |
| Еда удаляется из `state.foods` | |
| `ticksWithoutFood` сбрасывается | |

#### 16.6 `processTick` (интеграционный)

| Тест | Что проверяется |
|------|-----------------|
| Один полный тик: змейка двигается на 1 клетку | Новая позиция головы, хвост удалён |
| Тик со столкновением со стеной → `alive = false` | `deathReason = 'Врезалась в стену'` |
| Тик с поеданием еды → рост + очки | |
| `tickCount` увеличивается | |

#### 16.7 Спавн еды

| Тест | Что проверяется |
|------|-----------------|
| `spawnFood` возвращает запрошенное количество еды | Или меньше, если не хватает места |
| Ни одна еда не на стене | `food.pos` не совпадает с `state.walls` |
| Ни одна еда не на змейке | `food.pos` не совпадает с сегментами |
| Расстояние Чебышёва между любыми сущностями еды > 1 | |
| Вся еда внутри границ поля | |
| `age`, `clockNum`, `reproductionCount` инициализированы корректно | |

#### 16.8 Генерация стен (BFS-связность)

| Тест | Что проверяется |
|------|-----------------|
| `validateWalls` для пустого списка стен → `true` | |
| `validateWalls` для стен, создающих изолированную зону → `false` | Стена от края до края |
| `generateWalls` всегда возвращает валидные стены (или пустые) | Вызвать `validateWalls` на результат |
| Стены не в зоне безопасности змеек | Расстояние Чебышёва до exclusionZones > safeRadius |

#### 16.9 Формулы

| Тест | Что проверяется |
|------|-----------------|
| `getTargetScore(1)` = `Math.floor(5 × 1 + 20)` = 25 | |
| `getCumulativeTargetScore(3)` = 25 + 30 + 35 = 90 | |
| `getWallClusterCount(3)` = `Math.floor(1.2 × 3 + 2)` = 5 | |
| `getWallLength(5)` = `Math.floor(1.2 × 5 + 3)` = 9 | |
| `getInitialFoodCount(1, 1)` = `Math.floor(1.5 × 1 + 10 − 1)` = 10 | |
| Все формулы используют `Math.floor` | |

#### 16.10 `checkLevelComplete`

| Тест | Что проверяется |
|------|-----------------|
| Одиночная: `score >= cumulativeTarget` → `true` | |
| Одиночная: `score < cumulativeTarget` и alive → `false` | |
| Одиночная: `alive = false` → `true` | |
| Одиночная классика: `level >= 10` → завершение игры | |
| Одиночная выживание: `level >= 100` → завершение игры | |
| Одиночная выживание: при достижении цели уровня выполняется автопереход без паузы/модалки | |
| Мультиплеер: 1 змейка жива → `true` | |
| Мультиплеер: `timeLeft <= 0` → `true` | |
| Мультиплеер: `level >= 10` → завершение матча | |
| Мультиплеер: 2+ живы и время есть → `false` | |

## 18. Актуальные уточнения и журнал решений

Раздел фиксирует только актуальные уточнения, которые уже интегрированы в основное ТЗ.

1. Максимум людей-игроков: **2**. Режим наблюдателя (0 людей) поддержан.
2. Округление формул: всегда `Math.floor()`.
3. Лимит уровней:
   - классика (1 игрок) — до уровня **10**;
   - мультиплеер/смешанный режим — до уровня **10**;
   - выживание (1 игрок) — до уровня **100**, с автоматическим переходом по достижению цели уровня без паузы.
   - поле выживания расширяется только до уровня **10**; canvas имеет максимальный размер с начала игры, а состояние доски между уровнями не пересоздаётся.
4. Еда:
   - единая модель `Food` + наследники (`AppleFood`, `RabbitFood`, `ChickenFood`, `MeatFood`);
   - возраст и фазы — в базовом классе;
   - размножение — общее поведение базового класса с возможностью переопределения в наследнике;
   - логика, ранее описанная для кроликов, трактуется как общее правило для еды;
   - при поедании любой еды голод змейки сбрасывается.
   - обычное размножение любой еды блокируется при общем количестве `13 + snakeCount − difficultyLevel`; гарантированный спавн каждого 100-го тика этот лимит игнорирует.
5. Яблоки (базовая еда):
   - `young` (зелёное): +1 очко, +1 сегмент;
   - `adult` (красное): +2 очка, +2 сегмента;
   - `old` (коричневое): +1 очко, +1 сегмент.
   - на уровне 1 являются единственным активным типом еды; с уровня 2 штатный спавн выбирает куриную еду с вероятностью 30%.
6. Куриная еда:
   - стадии используют общие возрастные границы: яйцо +1, цыплёнок +2, курица +3;
   - яйцо неподвижно, цыплёнок ходит раз в 3 тика в радиусе 5 от яйца, курица — раз в 2 тика без общего ограничения дальности;
   - курица движется к ближайшим яблокам, стараясь сохранять дистанцию 10 клеток от змеек, а в радиусе 5 активно убегает;
   - если яблок нет, выбирает направление с наименьшей плотностью змеек;
   - взрослая курица откладывает не более трёх яиц с теми же ограничениями плотности и соседства, что и яблоко;
   - на каждом тике взрослой стадии кладка проверяется с независимой вероятностью `3 / 50 = 0,06`, равномерной по ходам;
   - при наличии яйца, цыплёнка или другой курицы в радиусе 10 взрослая курица старается покинуть перенаселённую область, но никогда не выходит за пределы поля;
   - яблоко уменьшает возраст курицы на 10, но не ниже `age = 100`, уменьшает `reproductionCount` на 1, но не ниже 0, и не создаёт обязательную кладку.
7. Мясо:
   - неподвижно, отображается как 🍖, имеет единственную стадию `0..49`, даёт +1 очко и +1 сегмент;
   - естественно умершая на `age = 150` курица превращается в один кусок мяса;
   - погибшая от столкновения или самоукуса змейка создаёт `ceil(length / 3)` кусков на клетках тела;
   - умершая с голоду змейка мяса не создаёт.
8. Автодобавление взрослой еды:
   - при `foodCount < aliveSnakeCount`;
   - позиция выбирается максимально удалённой от голов змеек по Чебышёву;
   - при равенстве предпочтение равноудалённым позициям;
   - не чаще 1 раза за `hungerThreshold` тиков.
   - независимо от дефицита и лимитов размножения каждые 100 тиков добавляется новорождённая еда; вероятность курицы равна 30% при малом числе яблок, начинается с 60% после порога `min(2 × aliveSnakes, 10)` и линейно достигает 100% при 20 яблоках.
9. HUD:
   - структура и размещение остаются как в базовой версии (P1 слева, P2 справа, боты снизу);
   - ориентация HUD остаётся в мировых координатах (без поворота под стороны игроков);
   - статистика использует цвет соответствующей змейки, после смерти — её серый цвет;
   - после смерти всех людей смешанную игру можно быстро досчитать без промежуточного рендеринга и получить фактический результат партии.
10. Ключи конфигурации:
   - в актуальной версии ТЗ используются только ключи новой food-схемы;
   - legacy rabbit-ключи удалены из runtime-модели и не поддерживаются.
11. Состояние еды:
   - единственным источником истины является `GameState.foods`;
   - дублирующее поле `GameState.rabbits` и совместимые алиасы функций не используются.
12. Порядок следующих этапов:
   - сначала реализуется сетевой мультиплеер;
   - генетическое обучение реализуется после мультиплеера;
   - архитектура общего core сразу учитывает браузерные и серверные симуляции и будущее обучение.
13. Сетевой мультиплеер:
   - сервер является единственным источником истины и выполняет общий Engine;
   - клиент передаёт команды управления и получает снимки состояния;
   - транспорт — стандартный WebSocket-протокол, без Socket.IO;
   - HTTP API строится на Express, WebSocket gateway — на совместимом с Node.js WebSocket-сервере (`ws` как рекомендуемая реализация);
   - любой пользователь без регистрации может создать публичную комнату или приватную комнату с кодом;
   - в комнате не более 6 удалённых игроков и ботов суммарно; состав задаёт создатель;
   - матч начинается после ready-подтверждения всех подключённых игроков, их статусы отображаются в лобби;
   - наблюдатели не поддерживаются;
   - сервер отправляет снимок каждый тик, клиент использует prediction своей змейки и reconciliation;
   - при намеренном выходе змейка сразу заменяется ботом;
   - явный сетевой разрыв фиксируется сразу; «тихий» — после 5 секунд без heartbeat при ping раз в 2 секунды;
   - при технической потере соединения змейка останавливается, остаётся участником коллизий, голод продолжает действовать; игрок может вернуться в течение 10 секунд, после чего управление передаётся боту средней сложности;
   - человеку засчитываются только очки, набранные во время его управления; очки заменявшего бота не попадают в личный результат и таблицу рекордов;
   - все настроенные человеческие места должны быть заполнены и готовы; bot-слоты, помеченные как заменяемые игроками, ожидание не блокируют;
   - игрок может заменить помеченного бота только между раундами; личные очки игрока считаются с момента подключения отдельно от унаследованного результата игрового слота;
   - при отключении создателя управление комнатой переходит раньше всех подключившемуся человеку;
   - история сетевых матчей сохраняется через `MatchHistoryRepository`: SQLite в первой постоянной реализации, PostgreSQL в будущем;
   - пустая комната удаляется через 10 минут, завершённая сессия — из памяти через 5 минут после сохранения истории;
   - публичная история доступна без секретов, приватная и полная — по соответствующим токенам;
   - входящие WebSocket-сообщения ограничены 16 КБ;
   - первая версия работает в одном процессе, но комнаты и repository-порты проектируются с возможностью дальнейшего масштабирования.
