# Архитектурный план: сетевой мультиплеер и генетическое обучение

Документ фиксирует решения и открытые вопросы для следующих крупных этапов проекта. Он дополняет `docs/spec.md`, но не описывает уже реализованное поведение.

Статусы решений:

- **Принято** — решение утверждено и учитывается в архитектуре следующих этапов.
- **Рекомендовано** — базовый вариант предложен, но требует подтверждения перед реализацией соответствующего этапа.
- **Открытый вопрос** — выбор пока не сделан.

## 1. Порядок реализации

1. **Принято:** первым реализуется сетевой мультиплеер.
2. **Принято:** после мультиплеера реализуется полноценное генетическое обучение нейросетевых ботов.
3. **Принято:** архитектура монорепозитория и общих пакетов сразу должна учитывать оба этапа, чтобы серверный Engine, Arena и AI не пришлось повторно переносить или дублировать.

## 2. Целевая структура монорепозитория

### 2.1 Принятая схема верхнего уровня

```text
apps/
  web/                 браузерная игра и визуальные инструменты
  server/              HTTP API, WebSocket multiplayer, задания обучения

packages/
  core/                Engine, Arena, AI и в будущем genetic training
  contracts/           сериализуемые HTTP/WebSocket DTO и версии протоколов
```

На первом шаге не создаются дополнительные мелкие пакеты. Внутри `packages/core` сохраняется понятное разделение каталогов `engine`, `arena`, `ai`, а позднее добавляется `training`. Выделение новых npm-пакетов допускается только при появлении реальной независимой границы.

### 2.2 Обязательные границы

`packages/core`:

- не импортирует DOM, Canvas, `localStorage`, Express или WebSocket;
- не использует браузерные таймеры и прямой `Math.random()`;
- принимает RNG, настройки и другие зависимости явно;
- одинаково выполняется в браузере, Web Worker, Node.js и Worker Thread;
- содержит единственную реализацию правил игры.

`packages/contracts`:

- содержит только сериализуемые типы и функции проверки версии протокола;
- не экспортирует доменные Entity с методами;
- не передаёт `GameState` напрямую по сети;
- определяет отдельные DTO для снимков, команд, ошибок и событий соединения.

`apps/web`:

- содержит Renderer, UI, ввод, локальное хранилище и сетевой клиент;
- в сетевом матче не является источником истины для игрового состояния.

`apps/server`:

- содержит Express-приложение, WebSocket gateway, комнаты и серверные адаптеры;
- запускает общий Engine из `packages/core`;
- позднее управляет заданиями обучения, но сам генетический цикл остаётся в `packages/core/training`.

### 2.3 План миграции без большого одномоментного переноса

1. Зафиксировать workspace-структуру и сборочные команды.
2. Выделить сериализуемые multiplayer contracts.
3. Подготовить публичный API общего core без DOM-зависимостей.
4. Перевести браузерное приложение на импорт общего core.
5. Проверить одинаковый детерминированный прогон общего ядра в браузерных тестах и Node.js.
6. Подключить общий core к авторитетным серверным комнатам.

Фактические перемещения файлов и изменения конфигурации выполняются отдельными этапами после явного согласования, поскольку это затрагивает структуру проекта и публичные импорты.

## 3. Сетевой мультиплеер

### 3.1 Принятые решения

1. Сервер **авторитетный**: только серверный Engine изменяет состояние матча и определяет результат.
2. Клиент отправляет команды управления, но не отправляет готовые координаты, очки или результат коллизий.
3. Сервер регулярно отправляет клиентам сериализуемые снимки состояния.
4. Для двустороннего обмена используется стандартный WebSocket-протокол, без Socket.IO.
5. Express используется как HTTP-слой для служебных маршрутов, проверки состояния сервера и в будущем API лобби/истории/обучения.
6. WebSocket-сервер подключается к тому же HTTP-серверу; рекомендуемая Node.js-реализация — библиотека `ws`.
7. Сервер использует те же Engine и настройки, что браузерная и headless-версии игры.
8. Боты сетевого матча выполняются на сервере.
9. Поддерживаются публичные комнаты из общего списка и приватные комнаты, доступные по коду.
10. Любой пользователь без регистрации может создать комнату.
11. В сетевой комнате находится не более 6 змеек суммарно: удалённые игроки и боты вместе.
12. Создатель комнаты задаёт количество мест игроков, количество ботов и остальные настройки матча; сумма игроков и ботов не превышает 6.
13. Режим наблюдателя в первой версии не поддерживается.
14. Матч стартует после ready-check: все подключённые участники-люди должны нажать кнопку «Играть»; до старта отображаются состав комнаты и статусы готовности.
15. История сетевых матчей сохраняется на сервере.

Добавление Express, `ws`, npm workspaces и изменение конфигурации проекта требует отдельного согласования непосредственно перед реализацией.

### 3.2 Авторитетный цикл матча

```text
WebSocket input
  → проверка сообщения и участника
  → command buffer комнаты
  → серверный тик
  → применение допустимых команд
  → Engine.processTick()
  → формирование GameSnapshotDTO
  → рассылка подключённым участникам
```

Каждая команда клиента содержит минимум:

```ts
interface DirectionCommandDTO {
  type: 'direction';
  matchId: string;
  playerId: string;
  sequence: number;
  direction: 'up' | 'down' | 'left' | 'right';
}
```

Каждый снимок содержит минимум:

```ts
interface GameSnapshotDTO {
  protocolVersion: number;
  matchId: string;
  tick: number;
  acknowledgedInputByPlayer: Record<string, number>;
  status: 'waiting' | 'playing' | 'round-complete' | 'game-complete';
  level: number;
  levelTimeLeft: number;
  snakes: SnakeSnapshotDTO[];
  foods: FoodSnapshotDTO[];
  walls: PositionDTO[];
}
```

Снимок не содержит методов Entity и не используется сервером как мастер-состояние. Это транспортное представление текущего серверного `GameState`.

Сетевой контракт поддерживает значения `NetworkFoodKind = 'chicken' | 'meat'`. Возраст из снимка определяет значок яйца, цыплёнка, курицы или срок жизни мяса; `originPos` и счётчики движения и размножения остаются серверным состоянием и клиенту для отрисовки не передаются. Все перемещения куриной еды, поедание яблок, превращение умерших сущностей в мясо и seeded RNG рассчитывает только авторитетный сервер, после чего клиент получает готовые позиции в очередном снимке.

Враги передаются отдельно от еды через `EnemySnapshotDTO`. Для ежа снимок содержит `enemyId`, вид, левую верхнюю позицию области, размер `2×2` и направление отображения. Планируемая клетка, обзор, выбор цели, столкновения и seeded RNG остаются внутренним состоянием авторитетного Engine; клиент получает только уже рассчитанное состояние текущего тика.

### 3.3 Требования к MVP протокола

- **Принято:** сервер отправляет полный снимок на каждом игровом тике.
- **Принято:** клиент выполняет prediction собственной змейки для отзывчивого управления.
- **Принято:** серверный снимок всегда имеет приоритет; клиент согласует предсказанное состояние по `acknowledgedInputByPlayer` и `sequence`.
- **Рекомендовано:** начать с JSON-сообщений, чтобы протокол было просто отлаживать.
- `protocolVersion` в каждом handshake и снимке.
- `sequence` для команд и подтверждение последней обработанной команды.
- ping/pong и закрытие потерянных соединений.
- уникальный reconnect token, не совпадающий с отображаемым именем игрока.
- серверная валидация размера сообщений, типа команды и принадлежности игрока матчу.
- остальные змейки отображаются с интерполяцией между серверными снимками; их состояние клиент не предсказывает.

Delta-снимки, бинарный протокол и горизонтальное масштабирование откладываются до измерения реального трафика и нагрузки.

### 3.4 Утверждённые правила комнат и подключений

| № | Вопрос | Принятое решение |
|---:|---|---|
| 1 | Создание матчей | Есть публичный список комнат. Любой пользователь может создать публичную или приватную комнату; для приватной нужен код. |
| 2 | Максимум участников | До 6 змеек суммарно: удалённые игроки и боты. Это сетевой лимит и не меняет отдельно правила локального режима. |
| 3 | Смешанные матчи | Создатель выбирает количество мест игроков и ботов; сумма не больше 6. |
| 4 | Наблюдатели | В первой версии отсутствуют. |
| 5 | Намеренный выход | Змейка сразу передаётся под управление серверного бота. |
| 5 | Техническая потеря соединения | Явный разрыв фиксируется сразу. При «тихой» потере соединения разрыв фиксируется после heartbeat timeout; затем змейка останавливается на период ожидания переподключения. |
| 6 | Переподключение | Место и reconnect token сохраняются 10 секунд; затем змейка передаётся боту. |
| 7 | Старт матча | Автоматически после того, как все подключённые участники-люди нажали «Играть». В комнате видны подключения и ready-статусы. |
| 8 | Вход в начатый матч | Только между раундами и только если создатель включил настройку «Разрешить игрокам заменять ботов». |
| 9 | Регистрация | Не требуется; используются имя, временный player id и секретный reconnect token. |
| 10 | История | История сетевых матчей сохраняется на сервере. |
| 11 | Частота снимков | Полный серверный снимок каждый тик. |
| 12 | Prediction | Для собственной змейки обязателен client prediction с последующей reconciliation по серверному снимку. |
| 13 | Результат при техническом отключении | Личный результат человека считается только за время его управления; дальнейшие очки заменившего бота человеку не начисляются и в таблицу рекордов не попадают. |
| 14 | Масштабирование | Первая версия работает в одном серверном процессе, но границы комнат, репозитории и протокол не должны препятствовать последующему распределению матчей между экземплярами. |

WebSocket работает поверх TCP и не сообщает приложению об отдельном потерянном сетевом пакете. Поэтому правило «при потере пакетов» технически трактуется как отсутствие heartbeat/разрыв соединения, обнаруженный сервером. Кратковременная TCP-задержка сама по себе не переводит змейку в остановленное состояние до срабатывания connection timeout.

### 3.5 Модель комнаты и лобби

Комната хранит:

- идентификатор, название и видимость `public/private`;
- случайный приватный код, который не публикуется в общем списке;
- настройки игры;
- число человеческих мест и ботов, суммарно не более 6;
- bot-слоты с признаком `replaceableByPlayerBetweenRounds`;
- создателя комнаты;
- участников со статусами `connected`, `ready`, `reconnecting`, `replaced-by-bot`;
- текущий матч и номер раунда.

Публичный список показывает только публичные комнаты и безопасную сводку: название, число подключённых игроков, число ботов, вместимость, состояние ожидания/игры и возможность присоединения. Reconnect token и приватный код в список не попадают.

Все настроенные человеческие места должны быть заполнены. Бот считается готовым автоматически, а помеченный как заменяемый bot-слот не блокирует старт в ожидании человека. Новый матч начинается, когда все человеческие места заполнены и все подключённые люди готовы. До старта создатель может уменьшить число человеческих мест или заменить пустые места ботами. После изменения состава или настроек ready-статусы людей сбрасываются.

### 3.6 Отключение и замена ботом

1. Намеренный выход подтверждается отдельным сообщением или согласованным WebSocket close code и сразу передаёт змейку боту средней сложности (`basic`).
2. Явный технический разрыв фиксируется сразу. Для «тихой» потери связи сервер отправляет ping каждые 2 секунды и считает соединение потерянным после 5 секунд без pong или другого сообщения.
3. После обнаружения технического разрыва участник переходит в `reconnecting`, змейка останавливается, а сервер запускает таймер 10 секунд.
4. Во время остановки змейка остаётся живой и видимой, её тело участвует в обычных коллизиях, а таймер уровня и голод продолжают отсчитываться. Она может погибнуть по обычным правилам и не восстанавливается при переподключении.
5. До истечения таймера reconnect token возвращает управление той же змейкой и сохраняет место участника. Для продолжения движения требуется новая команда игрока.
6. После таймера управление той же змейкой получает бот средней сложности (`basic`).
7. Если bot-слот помечен как заменяемый, новый игрок может занять его только на границе раундов.
8. Если создатель комнаты отключился, роль передаётся человеку, который раньше остальных подключился к комнате. Во время активного матча создатель не имеет особых игровых полномочий.
9. История матча хранит момент отключения, периоды управления человеком/ботом и факт замены.

### 3.7 Учёт очков при смене управляющего

Игровой слот змейки сохраняет общий счёт, длину и победы, необходимые для продолжения матча и определения результата раунда. Дополнительно сервер хранит интервалы управления:

```ts
interface ControlPeriodDTO {
  controllerType: 'human' | 'bot';
  controllerId: string;
  startedAtTick: number;
  endedAtTick?: number;
  scoreGained: number;
}
```

Правила:

1. Личный результат человека содержит только очки, набранные в его интервалах управления.
2. Очки бота после замены не прибавляются отключившемуся человеку и не создают запись в таблице рекордов.
3. Игрок, заменивший бота между раундами, занимает существующий игровой слот, но его личный результат начинается с момента подключения.
4. Накопленный технический результат слота продолжает использоваться Engine для раундов и побед, но унаследованные очки бота не считаются личными очками нового игрока.
5. История матча хранит все периоды управления для аудита результата.

Текущее состояние реализации: `MatchSession` закрывает и открывает периоды при разрыве,
переподключении, передаче управления боту и замене bot-слота между раундами. После
10-го раунда он формирует `MatchHistoryDTO`; сохранение DTO через repository относится
к следующему шагу.

### 3.8 Хранение истории

1. Сервер использует порт `MatchHistoryRepository`.
2. Для тестов применяется `InMemoryMatchHistoryRepository`.
3. Первая постоянная реализация — SQLite; переход к PostgreSQL не меняет use-case и WebSocket-слои.
4. Пустая ожидающая комната удаляется через 10 минут.
5. Завершённый `MatchSession` хранится в оперативной памяти 5 минут, после чего удаляется; постоянная история остаётся в repository.
6. Публичная краткая история публичных матчей доступна всем и не содержит технических секретов.
7. Полная история участника доступна по session/reconnect token.
8. История приватного матча доступна по отдельному history token.
9. Reconnect token, history token, приватный код, сетевой адрес и внутренние серверные данные никогда не входят в публичный ответ.

Текущее состояние реализации: сервер принимает `MatchHistoryRepository` через опции,
по умолчанию использует `InMemoryMatchHistoryRepository`, сохраняет финальный
`MatchHistoryDTO` асинхронно и ожидает начатые записи при корректной остановке.
Пустая ожидающая комната удаляется через 10 минут, завершённая `MatchSession` —
через 5 минут; оба интервала настраиваются для тестового окружения. Реализованы
`GET /api/matches` с краткими результатами публичных матчей и
`GET /api/matches/:matchId` с Bearer-аутентификацией. Reconnect token возвращает
только историю соответствующего человека, отдельный history token приватной
комнаты — полную историю. Repository хранит только SHA-256 хэши токенов.
`SqliteMatchHistoryRepository` использует встроенный `node:sqlite`, хранит записи
в WAL-режиме и переживает перезапуск процесса. При запуске сервера адаптер
включается переменной `MATCH_HISTORY_DB`; без неё dev-сервер использует память.

### 3.9 Client prediction и reconciliation

1. Клиент сразу применяет введённое направление к визуальному прогнозу собственной змейки и отправляет команду с возрастающим `sequence`.
2. Сервер обрабатывает команду на границе тика и возвращает номер последней подтверждённой команды.
3. Получив снимок, клиент принимает серверное состояние, удаляет подтверждённые команды и повторно применяет оставшиеся команды локального буфера.
4. Клиент не подтверждает самостоятельно еду, рост, смерть, голод, столкновения и результат раунда.
5. Небольшая коррекция позиции сглаживается; смерть, изменение длины и существенное расхождение применяются сразу.
6. Остальные змейки только интерполируются между серверными снимками.

Текущее состояние реализации: удалённые живые змейки одинаковой длины плавно
интерполируются между двумя последовательными снимками. Пропущенный тик, смерть,
изменение длины или смещение сегмента больше одной клетки применяются сразу.
Локальная змейка использует текущий серверный снимок и неподтверждённую команду.
Небольшая reconciliation-коррекция сглаживается от последней реально отрисованной
позиции; новая команда игрока немедленно отменяет сглаживание локальной змейки.

### 3.10 Ограничения WebSocket

- ping каждые 2 секунды;
- heartbeat timeout 5 секунд для «тихой» потери связи;
- явный разрыв фиксируется сразу;
- окно переподключения 10 секунд начинается после фиксации разрыва;
- максимальный размер входящего WebSocket-сообщения 16 КБ;
- неизвестный тип, невалидный JSON, превышение размера или нарушение принадлежности матчу отклоняются;
- повторные нарушения закрывают соединение.

### 3.11 Масштабируемость после MVP

Первая версия использует один процесс, однако:

- каждая комната инкапсулирована в `MatchSession` и не обращается к глобальным коллекциям напрямую;
- поиск комнат, история матчей и владение матчем скрыты за репозиториями;
- WebSocket gateway не содержит правил Engine;
- Express раздаёт production-сборку из `dist` (или `STATIC_DIR`), поэтому одиночная игра, HTTP API и `/ws` доступны с одного origin;
- снимки и команды имеют версию протокола;
- `serverInstanceId` и `matchId` не зависят от адреса процесса;
- в будущем репозитории можно заменить общими хранилищами, а комнаты распределить по нескольким процессам с маршрутизацией соединений.

## 4. Генетическое обучение — браузерные этапы G1–G10 реализованы

### 4.1 Уже принятые продуктовые требования

1. Реализация начинается после сетевого мультиплеера.
2. Должны существовать визуальный браузерный и серверный headless-режимы.
3. Скорость визуального режима настраивается от `1x` до `1000x`.
4. Симуляция и рендер разделяются: обучение считается headless, а Canvas независимо доигрывает демонстрацию лучшего кандидата последнего завершённого поколения на выбранной скорости. Следующее поколение заменяет показанное только после завершения уже запущенной партии; validation-чемпион учитывается отдельно.
5. После обучения выводятся графики и таблицы поколений.
6. Обученные веса сохраняются через универсальный асинхронный API.
7. Первая реализация хранилища использует `localStorage` и позволяет скачать файл модели.
8. Будущая реализация использует HTTP backend без изменения UI и формата модели.
9. Браузерное обучение должно выполняться вне основного UI-потока; серверное — вне Express event loop.
10. Engine, Arena, AI и training core переиспользуются между браузером и Node.js.
11. Экран лаборатории содержит кнопку, открывающую отдельное окно с инструкцией по настройке, сохранению и запуску модели.
12. Помимо визуального режима лаборатория поддерживает фоновый прогон без Canvas-анимации и без обновления таблицы/графика на каждом поколении. Число поколений не имеет прикладного верхнего ограничения.
13. Фоновый прогон запрашивает браузерный Screen Wake Lock и явно показывает его состояние. Поскольку браузер может снять блокировку у скрытой вкладки, для гарантированного ночного прогона пользователь дополнительно отключает сон средствами ОС.
14. После успешного завершения лучшая модель автоматически сохраняется через тот же асинхронный репозиторий, который используется ручным сохранением. Полный отчёт поколений хранится в памяти до ухода с экрана и доступен для выгрузки CSV.

### 4.2 Архитектурные инварианты, которые учитываются уже при мультиплеере

- RNG среды, RNG алгоритма кандидата и RNG генетического оператора разделены.
- Один и тот же seed и конфигурация дают одинаковый результат в браузере и Node.js.
- Arena не зависит от Renderer или transport DTO.
- Метрики Arena сериализуемы и не содержат DOM/Node.js объектов.
- Нейросеть и схема наблюдения имеют версии.
- Веса хранятся отдельно от runtime-объекта алгоритма.
- Training runner сообщает прогресс событиями/колбэками и не управляет UI напрямую.
- Хранилище моделей и исполнитель обучения являются разными портами.

### 4.3 Утверждённый вариант первой версии

- классический генетический алгоритм;
- настраиваемая полносвязная MLP с фиксированной топологией внутри одного задания;
- турнирный отбор;
- поколенческая замена с элитизмом;
- равномерное скрещивание весов;
- гауссова мутация весов и bias;
- гибридная оценка: одиночные прогоны, матчи против эвристических ботов и матчи внутри поколения;
- одинаковые меняющиеся по поколениям training seed и отдельные постоянные validation seed;
- Web Worker в браузере и пул Worker Threads на сервере.

Первая реализация до этапа G10 включает браузерное обучение и отчёты. Серверный
runner и HTTP API выполняются отдельным последующим этапом. Начальная
конфигурация: популяция 128, 100 поколений, MLP `input → 16 → 8 → 3`, `tanh`,
элита 8, турнир 4, вероятность скрещивания 0,25, вероятность мутации отдельного
параметра 0,02 и стандартное отклонение гауссовой мутации 0,05.
Кандидаты одного поколения оцениваются на шести одинаковых training seed; новый
набор детерминированно выводится из базового seed и номера поколения. Каждые 10
поколений лучший кандидат поколения проверяется на пяти постоянных validation
seed с той же смесью сценариев и игровыми правилами. Лучший validation-результат
определяет сохраняемого чемпиона. Лимит одного прогона — 10 000 тиков.

Гибридная оценка распределяется так: 50% одиночные прогоны, 30% матчи против
эвристических ботов `basic` и `solid`, 20% матчи кандидатов поколения. Ошибки
управления ботов по умолчанию выключены для чистой оценки политики и могут быть
включены отдельным validation-сценарием устойчивости.

Fitness — нормализованная взвешенная сумма очков, побед, ограниченного вклада
выживания, прогресса к еде и штрафа за смерть. Настройки fitness входят в
`TrainingConfig` и сохраняются вместе с моделью. В браузере вычисления идут в
Web Worker; основной поток в визуальном режиме показывает validation replay
чемпиона. Фоновый режим не запускает replay, обновляет текстовый прогресс примерно
на каждом проценте и после завершения строит график и таблицу по выборке не более
200 точек; CSV при этом содержит все поколения. При скорости выше `8x` тики
считаются пакетами, а Canvas получает редкие кадры.

Модель хранит версию формата, версию наблюдения, топологию, веса, конфигурацию
и validation-метрики. Асинхронный repository текущей версии использует
`localStorage` и поддерживает импорт/экспорт JSON завершённых моделей. Полный
checkpoint популяции хранится отдельно в IndexedDB, поскольку размер всей
популяции не соответствует ограничениям `localStorage`. На границе поколения
сохраняются популяция, validation-чемпион, его validation fitness, отчёты и
состояние RNG; завершённые модели
продолжают использовать repository на основе `localStorage`.

### 4.4 Реализованный браузерный этап G10

#### Параллельное вычисление

1. Генетическим циклом и RNG генетических операторов владеет один coordinator
   Worker. Оценки кандидатов и сценариев выполняет пул evaluation Worker; main
   thread остаётся только UI-слоем.
2. В лаборатории доступны режимы количества evaluation Worker:
   - `Автоматически`: `max(1, hardwareConcurrency - 2)`; если браузер не сообщил
     число ядер, используется один Worker;
   - `Вручную`: от 1 до `max(1, hardwareConcurrency - 1)`.
   Для компьютера с 12 ядрами автоматический режим выбирает 10 Worker, ручной
   допускает до 11. Coordinator не входит в показанное пользователю число.
3. Фактическое число запущенных Worker, партий в секунду, тиков в секунду,
   длительность поколения и ожидаемое время завершения выводятся в прогрессе.
4. Задачи получают стабильный ключ `generation/candidate/scenario/seed`.
   Результаты применяются только в каноническом порядке, независимо от порядка
   завершения Worker. Один seed и одна конфигурация должны давать одинаковый
   генетический результат при любом числе Worker.
5. Сбой evaluation Worker приводит к однократному повтору его текущей задачи;
   повторный сбой завершает обучение понятной ошибкой, не создавая частичный
   результат поколения.

#### Автосохранение и точное продолжение

1. Завершённая модель, текущий validation-чемпион и полное состояние обучения
   сохраняются раздельно через асинхронные repository-порты.
2. Полный versioned checkpoint содержит: id прогона, номер последнего полностью
   завершённого поколения, целевое число поколений, конфигурацию, всю следующую
   популяцию с id и геномами, validation-чемпиона, его поколение и fitness,
   состояние RNG генетических
   операторов, отчёты и ссылку на исходную модель при дообучении.
3. Checkpoint создаётся только на границе полностью завершённого поколения.
   Поэтому восстановление не смешивает полные и частичные оценки.
4. Интервал автосохранения настраивается в диапазоне 1–100 поколений; default —
   10. При штатной паузе/отмене сначала завершается текущее поколение и затем
   сохраняется checkpoint. После аварийного закрытия теряется не больше
   выбранного интервала.
5. Browser implementation хранит checkpoint в IndexedDB и только по одному
   последнему checkpoint на каждый незавершённый прогон. Сохранённые модели
   продолжают использовать существующий `localStorage` repository. Оба порта
   позднее заменяются HTTP API без изменения training core.
6. На каждом checkpoint текущий validation-чемпион автоматически обновляется в
   хранилище моделей под стабильным id данного прогона. После успешного окончания
   сохраняется финальная модель, а завершённый checkpoint удаляется.
7. Экран лаборатории показывает список незавершённых прогонов с поколением,
   целевым количеством, временем сохранения и действиями «Продолжить» и
   «Удалить». Возобновление может использовать другое число Worker, не меняя
   результат.
8. Текущий прогон, начатый версией без checkpoint-протокола, восстановить нельзя.

#### Дообучение сохранённой модели

1. Для совместимой сохранённой или импортированной модели доступно действие
   «Дообучить». Оно создаёт новый прогон и не перезаписывает исходную модель.
2. Первый кандидат новой популяции является точной копией модели, остальные —
   её независимо мутированные потомки. Исходная модель гарантированно входит в
   элиту первого поколения.
3. Разрешено менять правила Arena, seeds, число партий по сценариям и fitness-веса, параметры
   мутации/отбора и число поколений. Версия observation, число входов/выходов и
   topology должны совпадать; несовместимость показывается до запуска.
4. Новая модель хранит происхождение: `parentModelId`, исходный fitness и
   параметры начатого дообучения.

#### Настройки fitness

Лаборатория выводит все коэффициенты фактически используемой формулы:

```text
runFitness =
    score * weights.score
  + foodApproachProgress * weights.approach
  + levelsWon * weights.wins
  + min(1, survivedTicks / maxTicks) * weights.survival
  + (aliveAtEnd ? weights.aliveAtLimit : -weights.death)
```

Настраиваются существующие поля `score`, `approach`, `wins`, `survival`,
`aliveAtLimit` и `death`; все значения неотрицательные. Defaults:
`1 / 0.25 / 100 / 10 / 20 / 5`. `approach` применяется к ограниченному
прогрессу до отслеживаемой еды: повторное прохождение уже достигнутого расстояния
не награждается. UI показывает формулу с текущими значениями и
предупреждает, что слишком большой survival/alive reward может научить сеть
избегать игры, а не набирать очки. Число партий по сценарию задаёт фактическую
выборку и долю одиночных, эвристических и cohort-прогонов в среднем fitness.
Живая змейка, достигшая искусственного лимита Arena, получает полный survival и
alive bonus без штрафа. Устаревшее поле `cycle = 0` хранится только для
совместимости артефактов версии 1 и не участвует в формуле.

#### Визуальная компоновка лаборатории

1. HUD над Canvas всегда резервирует три строки одинаковой высоты и не меняет
   размер при обновлении значений:
   - рекорд всего обучения: поколение, training fitness и validation fitness;
   - показываемый чемпион: поколение, fitness и основные средние метрики;
   - текущая Canvas-партия: тик, очки, съеденная еда, длина и состояние/причина
     смерти.
   До появления данных используются заполнители, перенос строк отключён.
2. В визуальном режиме Canvas находится сверху левой области, а таблица и график
   обучения — ниже него в той же прокручиваемой колонке. В фоновом режиме таблица
   и график занимают место Canvas. Панель настроек остаётся справа.
3. Таблица имеет видимые внешние границы и вертикальные/горизонтальные линии
   ячеек, закреплённую строку заголовков и подписи всех столбцов. График имеет
   сетку, подписанные оси `X — поколение` и `Y — fitness`, числовые деления и
   легенду серий.
4. Каждая настройка имеет русское пояснение, доступное при наведении мыши и при
   фокусе клавиатуры через `aria-describedby`. Подсказка объясняет назначение,
   влияние на качество/скорость, допустимые значения и значение `0`, если оно
   отключает соответствующий сценарий или награду. На touch-устройствах та же
   подсказка открывается нажатием на значок информации.

### 4.5 Полный реестр решений и открытых вопросов генетического алгоритма

#### Оптимизатор

1. Классический GA, Evolution Strategies или NEAT.
2. Нужно ли поддерживать несколько оптимизаторов в первой версии или только один.
3. **Решено для G10:** совместимую модель можно дообучать с другими правилами и
   коэффициентами, но без изменения observation version и topology.

#### Сеть и геном

4. Фиксированная сеть `input → 16 → 3` или настраиваемый список скрытых слоёв.
5. Допустимое минимальное и максимальное количество слоёв и нейронов.
6. Активации: только `tanh`, выбор `tanh/ReLU` или активация на каждый слой.
7. Эволюционируются только веса или в будущем также топология.
8. Формат весов в файле: массив JSON или `Float32` в base64.
9. Ограничивать ли веса диапазоном после мутации.
10. Нужны ли рекуррентные сети и память состояния.

#### Наблюдение и действия

11. Сохранить вход `visionSize² + длина + голод` или добавить новые признаки.
12. Можно ли настраивать `visionSize` для конкретного задания.
13. Добавлять ли направление, расстояние до границ, доступную площадь и данные соперников отдельными признаками.
14. Оставить три относительных действия или перейти к четырём абсолютным направлениям.
15. Как версионировать несовместимые схемы наблюдения.

#### Популяция и замена поколений

16. Размер популяции по умолчанию и допустимый диапазон.
17. Число элитных кандидатов или процент элиты.
18. Полная поколенческая замена, steady-state или схема `μ + λ`.
19. Нужен ли контроль генетического разнообразия и минимальной дистанции геномов.
20. Что делать при отсутствии улучшения: остановка, увеличение мутации или перезапуск части популяции.

#### Отбор

21. Турнирный, ранговый, рулетка или усечение.
22. Размер турнира или давление рангового отбора.
23. Могут ли элитные особи участвовать как родители без ограничений.
24. Допускается ли само-скрещивание.

#### Скрещивание

25. Равномерное, одноточечное, двухточечное или арифметическое.
26. Вероятность скрещивания.
27. Скрещивать веса послойно или как один плоский геном.
28. Как выбирать bias при скрещивании.

#### Мутация

29. Вероятность мутации одного веса.
30. Сила гауссова шума.
31. Вероятность полной случайной замены веса.
32. Одинаковые ли параметры мутации для weights и bias.
33. Постоянная, уменьшающаяся или адаптивная сила мутации.
34. Усиливать ли мутацию при стагнации.

#### Сценарии оценки

35. Одиночная змейка, несколько кандидатов поколения, эвристические соперники или гибрид.
36. Доли каждого сценария в гибридном режиме.
37. Число seed на кандидата и частота обновления набора seed.
38. Какие эвристики используются: `rookie`, `basic`, `solid`, `wise`.
39. Сколько кандидатов одного поколения одновременно играют на поле.
40. Round-robin, случайные группы или турнирная сетка.
41. Должны ли одинаковые кандидаты играть на симметрично переставленных стартовых позициях.
42. Используются ли отдельные validation seed, не влияющие на отбор.
43. Нужен ли curriculum с последовательным повышением сложности.

#### Правила Arena

44. Уровень, сложность, режим игры и размер поля.
45. Лимит тиков одного прогона.
46. Настраиваются ли количество еды, стены, голод и длина змейки отдельно от обычной игры.
47. Один фиксированный набор правил или набор сценариев с разными правилами.
48. Что считается завершением зависшего прогона и как обнаруживать циклы.

#### Fitness

49. Взвешенная сумма, лексикографический порядок или Pareto-отбор.
50. Веса очков, еды, времени жизни, длины, уровней и побед.
51. Штрафы за стену, самостолкновение, столкновение с другой змейкой, голод и цикл.
52. Ограничивать ли вклад выживания, чтобы сеть не училась только избегать риска.
53. Нормализовать ли метрики между разными правилами и уровнями.
54. Использовать среднее, медиану, минимум или нижний перцентиль по seed.
55. Как учитывать стабильность и дисперсию результата.

#### Остановка и контрольные точки

56. Фиксированное число поколений, достижение fitness или остановка по стагнации.
57. **Решено для G10:** настраиваемый интервал 1–100, default 10 поколений.
58. **Решено для G10:** один последний checkpoint каждого незавершённого прогона
    хранится в IndexedDB, модели остаются в `localStorage`.
59. Сохранять только чемпиона или также разнообразный top-N.
60. **Решено для G10:** нужны pause/resume и восстановление с последней полностью
    сохранённой границы поколения.

#### Визуализация и отчёты

61. Показывать текущего кандидата, чемпиона поколения или отдельный validation replay.
62. Частота промежуточных кадров при `16x–1000x`.

#### Хранение и сервер

## 5. План этапов

### Этап M1 — подготовка монорепозитория

- workspace-структура — базовая npm-конфигурация готова; перенос браузерного приложения в `apps/web` остаётся архитектурной уборкой и не блокирует единый deploy;
- contracts — готов версионированный пакет DTO, констант протокола и валидации настроек комнаты;
- общий core — готов пакет `@snake-game/core` с Engine, headless Arena, heuristic и neural AI без DOM-зависимостей;
- браузерное приложение использует публичный API `@snake-game/core`; Canvas-рендер и визуальный Arena runner остаются в web-слое;
- независимые build-команды — готовы для contracts, core и server; текущие тесты импортируют core через его публичный API;
- единый локальный `npm run dev` запускает web, server, watch-компиляцию и dev proxy;
- детерминированный headless-прогон проверен через браузерный тестовый контур и собранный CommonJS-пакет в Node.js.

### Этап M2 — multiplayer transport

- Express HTTP server и маршрут `/health` — готово;
- WebSocket gateway на `ws` по маршруту `/ws` — готово;
- обязательный первый handshake и проверка версии протокола — готово;
- JSON-валидация сообщений, текстовый формат и лимит 16 КБ — готово;
- ping/pong и закрытие соединения по heartbeat timeout — готово;
- выдача и проверка reconnect token, 10-секундное окно переподключения и замена ботом — готовы на сервере и в браузерном клиенте.

### Этап M3 — авторитетная комната

- in-memory реестр публичных/приватных комнат — готов;
- HTTP API создания комнаты и публичного списка — готов;
- WebSocket-вход по room id/приватному коду, выдача player id и reconnect token — готов;
- lobby ready-статусы и проверка заполнения всех человеческих мест — готовы;
- `MatchSession` и серверный command buffer — готовы;
- серверный tick loop на общем `@snake-game/core` — готов;
- полный snapshot и подтверждение обработанной `sequence` каждый тик — готовы;
- автоматический запуск матча после ready-check и завершение текущей сессии — готовы;
- переходы между раундами с повторным ready-check и полная серия из 10 раундов — готовы;
- серверное управление настроенными ботами и ботами, заменившими игроков, — готово.

### Этап M4 — интеграция браузерного клиента

- сетевой экран/лобби — готова базовая версия: список публичных комнат, создание публичной/приватной комнаты, вход по room id/приватному коду, состав и ready-статусы;
- WebSocket client — готов базовый транспорт: same-origin `/ws`, handshake, вход, ручной reconnect, ready, выход, команды с возрастающим `sequence` и валидация серверных сообщений;
- отображение серверных снимков на общем Canvas и сетевой HUD — готово;
- prediction/reconciliation собственной змейки — готов один предполагаемый шаг, удаление команды после серверного `acknowledgedInputByPlayer` и сглаживание небольшой серверной коррекции;
- визуальная интерполяция удалённых змеек между последовательными снимками — готова;
- автоматическое переподключение — готово: reconnect token хранится в памяти активной страницы, ввод останавливается, клиент повторяет handshake/reconnect до 10 секунд и показывает обратный отсчёт; успех фиксируется только после `room-joined`, по таймауту отображается передача управления боту;
- завершение раунда — готово: финальный снимок остаётся видимым, участники повторно подтверждают готовность, следующий раунд продолжается на том же Canvas;
- завершение серии — готов итоговый экран с победителем и сортировкой по победам/очкам; серверная история доступна через HTTP API.

### Этап M5 — боты и полировка multiplayer

- серверные боты и смешанные матчи — готовы;
- техническая остановка змейки, восстановление управления и замена ботом после 10 секунд — готовы;
- намеренный выход с немедленной передачей управления боту — готов;
- вход между раундами с заменой разрешённого bot-слота — готов: публичный список отмечает такую комнату доступной, новый игрок занимает стабильный slot и участвует в повторном ready-check;
- раздельный учёт очков периодов управления — готов; итоговая история сохраняется через in-memory или постоянный SQLite repository и доступна через защищённый HTTP API;
- дополнительные ограничения, нагрузочные и длительные тесты — не реализованы.

### Этап G1 и далее — генетическое обучение

Браузерные этапы G1–G10 реализованы: универсальная MLP, генетический training core,
Web Worker, validation replay, localStorage repository, JSON/CSV export, график
fitness и таблицы поколений, детерминированный пул evaluation Web Worker,
полные IndexedDB-checkpoint с pause/resume, дообучение совместимых моделей,
редактирование коэффициентов fitness и обновлённую компоновку лаборатории.
Checkpoint восстанавливает популяцию, отчёты и RNG без изменения результата;
число Worker можно изменить перед продолжением. Серверный Worker Threads runner
и HTTP API остаются отдельным следующим этапом.
